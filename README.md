# Pomomo Prototype

> 판타지 RPG의 **도입부 한 구간**을 구현한 Unity 프로토타입입니다.
> 마을 사람의 의뢰를 받아 약초를 모으고, 숲의 몬스터를 처치하고, 길을 잃은 아이를 도운 뒤,
> 본격적인 이야기의 시작점에서 끝납니다.
>
> **완성된 게임이 아니라, 게임 시스템을 어떻게 설계하고 검증했는지를 보여주는 것**이 목적입니다.
> 기능을 넓게 나열하기보다 몇 개의 시스템을 설계 근거가 설명 가능한 수준까지 만드는 쪽을 택했습니다.

## 플레이 흐름

```
마을 사람 → 약초 수집 의뢰       (수집형 목표)
         → 몬스터 처치 의뢰      (처치형 목표) → 골드 보상
상점      → 물약 구매            (골드 소비 → 인벤토리)
아이      → 잃어버린 엄마 찾기    (대화형 목표)
이장      → 본편 도입
```

세 종류의 퀘스트 목표가 **각각 다른 방식으로 완료를 판정**하지만(소지 여부 조회 / 처치 횟수 집계 / 대화 플래그), 이를 호출하는 `QuestGiver`는 하나의 코드로 모두 처리합니다.

**개발 기간**: 2026.08.25 ~ 2026.09.02
**환경**: Unity 6 (URP) / C# / Input System
**플레이 영상**: _(작업 완료 후 링크 추가)_

## 2. 설계 결정과 근거

이 문서에서 가장 중요한 부분입니다. 각 선택마다 **무엇을 고려했고 왜 그렇게 정했는지**를 기록합니다.

### 2.1 상호작용 판정 — 레이캐스트 대신 OverlapSphere + 내적

처음에는 레이캐스트를 고려했습니다. 이전에 아이템 줍기를 구현할 때 써본 방식이기도 했습니다.

다시 검토해보니 그 경험은 **조준점이 있는 1인칭 환경**에서의 것이었습니다. 이 프로젝트는 3인칭 탐험 게임이라 상황이 다릅니다.

- 조준점이 없어 플레이어가 어디를 향해 판정이 나가는지 감을 잡기 어렵습니다
- 씨앗·작은 아이템은 얇은 레이 하나로 자주 빗나갑니다
- 힐링 계열 게임은 조작이 관대해야 하는데, 정밀 조준을 요구하면 톤이 깨집니다

그래서 **주변 반경의 후보를 모은 뒤(`Physics.OverlapSphere`), 거리와 정면 여부로 점수를 매겨 하나를 고르는** 방식으로 갔습니다. 정면 여부는 플레이어의 forward 벡터와 대상 방향 벡터의 내적으로 판정합니다.

```csharp
Vector3 toTarget = (target.position - transform.position).normalized;
float facing = Vector3.Dot(transform.forward, toTarget); // 1=정면, 0=옆, -1=뒤
```

### 2.2 플레이어 이동 — CharacterController

Rigidbody도 검토했습니다. 특히 상호작용이 많은 게임이니 물리 기반이 낫지 않을까 싶었습니다.

검토 결과, **남은 상호작용(줍기·심기)에는 플레이어 쪽 물리가 필요하지 않았습니다.** 물리를 요구하던 "밀기"는 스코프에서 제외했고, 떨어뜨린 아이템 같은 개별 오브젝트는 플레이어의 이동 방식과 무관하게 Rigidbody를 붙일 수 있습니다.

| | CharacterController | Rigidbody |
|---|---|---|
| 넉백 | 직접 구현 (약 4줄) | `AddForce` 한 줄 |
| 평소 이동 | 정확하고 예측 가능 | 경사 미끄러짐, 벽 떨림 |
| 튜닝 | 속도 값 위주 | mass/drag/friction 조정 |
| 코드 구조 | Update에서 처리 | 입력 Update / 이동 FixedUpdate 분리 |

Rigidbody는 넉백 하나를 쉽게 만드는 대신 나머지 전부를 어렵게 만든다고 판단했습니다.
넉백은 속도 변수를 두고 시간에 따라 감쇠시키는 방식으로 직접 구현합니다.

### 2.3 매니저 구조 — 싱글톤은 하나만

매니저마다 싱글톤을 두는 구조를 먼저 떠올렸지만, 그렇게 하면 매니저끼리 서로 직접 참조하게 되어 결합도가 올라가고 초기화 순서에 의존하게 됩니다.

**GameManager 하나만 싱글톤으로 두고, 시스템 간 통신은 이벤트로 처리**합니다.
예: "식물이 다 자랐다" → 이벤트 발행 → 동반자 AI와 UI가 각자 반응. 서로를 몰라도 됩니다.

`[DefaultExecutionOrder(-100)]`을 붙여 다른 스크립트가 `Awake`에서 `Instance`에 접근할 때 초기화 순서가 보장되도록 했습니다. 유니티는 `Awake` 호출 순서를 보장하지 않기 때문입니다.

### 2.4 상태 전환 시 이벤트 발사 순서

`SetState`에서 **상태 갱신 → timeScale 적용 → 이벤트 발사** 순서를 지킵니다.
구독자가 이벤트를 받는 시점에는 세상이 이미 최종 상태여야 하기 때문입니다. 순서가 뒤집히면 핸들러 안에서 옛 값을 읽게 되고, 원인을 찾기 어려운 버그가 됩니다.

이벤트는 `Action<GameState, GameState>` 형태로 **이전 상태와 새 상태를 함께** 전달합니다. 구독자가 "어디서 왔는지"를 알아야 하는 경우가 많고, 나중에 추가하려면 모든 구독자를 수정해야 하기 때문입니다.

### 2.5 입력 추상화

Input System의 Action 기반으로 입력을 처리합니다. 코드가 키를 직접 참조하지 않고 액션(Move, Interact)만 참조하므로, 이후 다른 입력 방식으로 확장할 때 코드 변경 범위가 좁습니다.

### 2.6 씬 구성과 DontDestroyOnLoad

씬 전환이 있는 구성이므로 GameManager에 `DontDestroyOnLoad`를 적용했습니다. 이에 따라 지키는 규칙:

- GameManager는 씬 최상위에 배치 (자식 오브젝트에서는 동작하지 않음)
- 살아남는 객체는 상태와 이벤트만 보유하고, **씬 오브젝트 참조를 캐싱하지 않음** (씬 전환 후 죽은 참조가 됨)
- 이벤트 구독자는 `OnDisable`에서 반드시 해제 (해제 누락은 유니티에서 가장 흔한 누수 패턴)

### 2.7 카메라 — Cinemachine 채택

3인칭 카메라를 직접 구현할 수도 있었지만, **Cinemachine(공식 무료 패키지)을 사용**했습니다.

처음에는 카메라를 플레이어의 자식 오브젝트로 두는 방식을 썼습니다. 그런데 이 구조에서는 캐릭터가 이동 방향으로 회전할 때 **카메라도 함께 회전**해 방향 감각이 무너지는 문제가 있었습니다. 탐험 중심 게임에서는 특히 치명적입니다.

Cinemachine은 추적 대상과 회전을 분리해 관리하므로 이 문제가 구조적으로 사라집니다. 더불어 카메라 충돌 회피(벽에 카메라가 파묻히지 않도록 당겨주는 처리)와 댐핑이 기본 제공됩니다.

직접 구현하면 며칠이 걸릴 수 있는 영역이고, 이 프로젝트에서 보여주려는 것은 카메라 수학이 아니라 게임 시스템 설계입니다. **검증된 패키지에 맡기고 그 시간을 시스템 설계에 쓰는 것이 낫다고 판단**했습니다.

구성: `Orbital Follow`(위치) + `Rotation Composer`(회전), Input System 연동은 `CinemachineInputAxisController` 사용.

### 2.8 카메라 기준 이동

카메라를 마우스로 회전할 수 있게 되면서, 월드 기준 이동은 어색해졌습니다. 카메라를 90도 돌린 상태에서 W를 눌러도 여전히 월드 +Z로 이동해, 화면상으로는 옆으로 걷는 것처럼 보이기 때문입니다.

그래서 입력을 **카메라 기준으로 변환**합니다.

```csharp
Vector3 camForward = cameraTransform.forward;
Vector3 camRight   = cameraTransform.right;
camForward.y = 0f;   // 카메라가 아래를 내려다보므로 y 성분 제거
camRight.y   = 0f;
camForward.Normalize();   // y 제거로 줄어든 길이를 1로 복원
camRight.Normalize();

Vector3 direction = camForward * moveInput.y + camRight * moveInput.x;
```

`Normalize()`를 생략하면 **카메라 각도에 따라 이동 속도가 달라지는** 버그가 생깁니다. 카메라를 더 가파르게 내려다볼수록 수평 성분이 짧아지기 때문입니다.

정규화 조건도 신경 썼습니다. 대각선 입력이 1보다 길어질 때만 정규화하고, 무조건 정규화하지는 않습니다. 항상 정규화하면 게임패드 스틱을 살짝 밀었을 때(0.3 정도) 값이 1로 늘어나 **미세한 속도 조절이 불가능**해지기 때문입니다.

회전은 `Quaternion.LookRotation`으로 목표 회전을 구한 뒤 `Quaternion.Slerp`로 보간합니다. 목표값을 즉시 대입하면 방향 전환이 끊겨 보입니다. 입력이 없을 때(0벡터)는 `LookRotation`이 경고를 발생시키므로 조기 반환으로 걸러냅니다.

### 2.9 참조 주입 방식 — 상황에 따라 구분

카메라 참조를 `[SerializeField]`로 Inspector에서 주입하는 방식을 먼저 고려했으나, 두 가지 문제가 있었습니다.

- 할당을 누락해도 컴파일 시점에는 드러나지 않고 런타임 null로 이어집니다
- **프리팹은 씬 오브젝트 참조를 직렬화할 수 없습니다.** Player를 프리팹으로 만들면 씬의 카메라를 가리키던 참조가 인스턴스화 시점에 null이 됩니다

그래서 다음 기준으로 나눠 쓰기로 했습니다.

| 방식 | 적용 대상 |
|---|---|
| `[SerializeField]` 주입 | 같은 프리팹·계층 내부의 참조 (자식 모델, 부착 위치, 이펙트 프리팹) |
| `Awake`에서 1회 탐색 후 캐싱 | 씬에 하나뿐인 전역적 대상 (메인 카메라, 매니저) |

탐색 실패 시에는 `Debug.LogError`로 원인을 명시합니다. 그대로 두면 이후 이동 로직에서 맥락 없는 `NullReferenceException`이 발생해 원인 파악이 어려워지기 때문입니다.

### 2.10 상호작용 — 행동은 다형성으로, 알림은 이벤트로

상호작용 대상마다 하는 일이 다릅니다(베리는 수집, NPC는 대화). `PlayerInteractor`가 대상 종류를 판별해 분기하면, 대상이 늘어날 때마다 `PlayerInteractor`를 수정해야 합니다.

그래서 `Interactable` 추상 클래스에 `Interact()`를 선언하고, 각 대상이 구현하도록 했습니다. `PlayerInteractor`는 다음 한 줄만 실행합니다.

```csharp
target.Interact(gameObject);   // 무엇이 일어나는지는 알지 못함
```

대상이 몇 종류로 늘어나도 `PlayerInteractor`는 수정되지 않습니다. 현재 `BerryPickup`과 `QuestGiver` 두 종류가 이 구조 위에서 동작합니다.

**이벤트를 쓴 곳은 따로 있습니다.** 처음에는 상호작용 자체를 이벤트/델리게이트로 처리하는 방안을 고려했지만, 두 방식이 답하는 질문이 다르다고 판단했습니다.

| | 답하는 질문 |
|---|---|
| 다형성 | 이 대상이 **무엇을 할 것인가** (일대일 행동 위임) |
| 이벤트 | 이 일이 일어났음을 **누가 알아야 하는가** (일대다 알림) |

(부가적으로 C#의 `event`는 선언한 클래스 외부에서 `Invoke`할 수 없어, 상호작용 실행에는 애초에 적합하지 않았습니다.)

그래서 수집 사실의 **전파**에 이벤트를 사용했습니다. `BerryPickup`은 자신이 수집되었음을 알릴 뿐 누가 듣는지 모르고, `QuestGiver`는 개별 베리를 찾아다니지 않고 알림만 구독합니다.

```csharp
public static event Action OnAnyBerryCollected;   // BerryPickup
```

`static`으로 둔 이유는 베리 인스턴스가 다수이고, 구독자가 각 인스턴스를 개별 추적할 수 없기 때문입니다. 다만 `static` 이벤트는 씬 전환에도 소멸하지 않으므로 **구독 해제 누락 시 파괴된 객체의 핸들러가 목록에 남습니다.** `OnEnable`/`OnDisable` 짝을 반드시 지키도록 했습니다.

### 2.11 아이템 데이터 — ScriptableObject 분리

아이템 종류마다 스크립트를 만드는 구조(`BerryPickup`, `MushroomPickup`, …)를 먼저 작성했지만, **줍는 동작 자체는 모두 동일하고 다른 것은 데이터뿐**이라는 점이 드러났습니다. 종류가 늘어날 때마다 코드가 늘어나는 구조였습니다.

그래서 아이템 정보를 `ItemData`(ScriptableObject) 에셋으로 분리하고, 동작은 `ItemPickup` 하나로 통합했습니다.

```
스크립트 1개 (ItemPickup) + 데이터 에셋 N개 (Item_Berry, Item_Seed, …)
```

새 아이템을 추가할 때 **코드 작성이 필요 없습니다.** 에셋을 만들고 프리팹에 할당하면 됩니다. 아이템 정보는 에셋 파일 한 곳에만 존재하므로, 표시 이름을 바꿀 때도 한 곳만 수정합니다.

**식별은 문자열이 아니라 참조로 합니다.**

```csharp
if (collected != targetItem) return;   // 에셋 참조 비교
```

`displayName == "Berry"` 같은 문자열 비교는 표시 이름을 변경하는 순간 컴파일 오류 없이 조용히 깨집니다. ScriptableObject 에셋은 그 자체가 고유한 실체이므로 참조 비교가 정확하며, 이름 변경에도 영향받지 않습니다.

또한 열거형 비교에서 `questState <= QuestState.InProgress` 같은 **순서 의존 비교를 피하고 `==`를 사용**했습니다. 열거형 값의 선언 순서가 바뀌면 조건의 의미가 경고 없이 달라지기 때문입니다.

> **도구 선택 기준에 대한 부기**
> 이 프로젝트에서 ScriptableObject 기반 이벤트 시스템은 채택하지 않았으나(위 표 참조), 아이템 데이터에는 ScriptableObject를 채택했습니다. 같은 도구라도 **실제로 존재하는 문제를 푸는가**가 판단 기준이었습니다. 전자는 C# 이벤트로 이미 해결되는 문제였고, 후자는 데이터 중복이라는 실재하는 문제가 있었습니다.

### 2.12 인벤토리 — 자료구조 선택

인벤토리에서 가장 빈번한 연산은 **"특정 아이템을 몇 개 가지고 있는가"** 조회입니다. 퀘스트 조건 판정, UI 표시가 모두 이 질문을 합니다.

| 후보 | 개수 조회 | 비고 |
|---|---|---|
| `List<ItemData>` | O(n) — 전체 순회 필요 | 획득 순서는 보존 |
| 슬롯 배열 | O(n) | 격자 UI에 적합, 빈 칸 관리 필요 |
| `Dictionary<ItemData, int>` | **O(1)** | 종류별 집계에 직결 |

지배적 연산이 조회이므로 `Dictionary<ItemData, int>`를 선택했습니다. 아이템 종류가 늘어나도 조회 비용이 일정합니다.

구현 시 유의한 점:

- `items[key]` 직접 접근은 없는 키에서 `KeyNotFoundException`을 발생시키므로, 조회에는 `TryGetValue`를 사용했습니다.
- 수량이 0이 되면 키 자체를 제거합니다. 그대로 두면 `Item_Berry → 0` 같은 의미 없는 항목이 누적되어 UI 순회 시 빈 항목으로 노출됩니다.

### 2.13 사건 집계에서 상태 조회로 — 퀘스트 진행도

초기 구현은 수집 **이벤트를 집계**하는 방식이었습니다(`collectedCount++`). 테스트 중 다음 결함이 드러났습니다.

> 퀘스트 수락 전에 아이템을 먼저 획득하면, 실제로는 소지하고 있음에도 진행도가 0으로 표시됩니다.

집계 조건을 완화하면 반대 문제가 발생합니다. 획득 후 아이템을 소비하거나 버려도 집계는 그대로 남아, 아이템 없이 퀘스트가 완료됩니다.

근본 원인은 **사건을 세고 있었다는 점**이었습니다. 사건 집계는 하나라도 누락되면 복구되지 않고, 발생 순서에 민감하며, 되돌릴 수 없습니다.

인벤토리 도입 후 **상태 조회 방식**으로 전환했습니다.

```csharp
int count = inventory.GetCount(quest.targetItem);   // 묻는 시점의 사실만 확인
```

언제 획득했는지, 몇 번에 걸쳐 모았는지가 조건에 영향을 주지 않습니다. 소비하면 조건이 자연히 깨집니다.

전환 결과 `QuestGiver`의 필드 하나, 메서드 하나, 이벤트 구독·해제 두 줄이 제거되어 **코드가 오히려 짧아졌습니다.**

### 2.14 설정 데이터와 런타임 상태의 분리

퀘스트 정보를 `QuestData`(ScriptableObject)로 분리하면서, **진행 상태(`QuestState`)는 ScriptableObject에 두지 않았습니다.**

ScriptableObject는 에셋 파일이므로 런타임 변경이 파일에 기록됩니다. 에디터에서는 플레이 종료 후에도 값이 되돌아가지 않아, 다음 실행이 이미 완료된 상태로 시작됩니다. 또한 같은 에셋을 참조하는 인스턴스가 여럿이면 상태를 공유하게 됩니다.

| 성격 | 위치 | 예 |
|---|---|---|
| 설정 데이터 (불변) | ScriptableObject | 대사, 목표 아이템, 필요 수량 |
| 런타임 상태 (가변) | MonoBehaviour | 현재 퀘스트 진행 상태 |

### 2.15 상태머신 — Enter / Tick / Exit 구조

동반자와 적은 행동은 다르지만 **상태를 갖고 전이한다는 골격은 같습니다.** 그래서 상태머신을 먼저 설계하고 양쪽에 재사용하는 순서로 진행했습니다.

```csharp
public abstract class State
{
    public virtual void Enter() { }
    public virtual void Tick() { }
    public virtual void Exit() { }
}
```

**enum + switch로 처리하지 않은 이유**는 `Enter`/`Exit` 때문입니다. 상태에 들어가는 순간 한 번만 해야 하는 일(애니메이션 시작, 목표 설정)과 나올 때 한 번만 해야 하는 일(정리)이 있는데, switch 구조에서는 "지금 막 진입했는가"를 판별할 방법이 없어 별도 플래그를 계속 관리하게 됩니다. 상태가 늘어날수록 그 뒷정리 코드가 분기문을 뒤덮습니다.

**전이 판단은 각 상태가 스스로 합니다.** `CompanionAI`는 거리 조건을 알지 못하고, 각 상태의 `Tick`이 조건을 확인해 전이를 요청합니다. 상태를 추가해도 `CompanionAI`는 수정되지 않습니다. `PlayerInteractor`가 대상 종류를 모르게 설계한 것과 같은 구조입니다.

**상태 객체는 `Awake`에서 한 번 생성해 재사용합니다.** 전이할 때마다 `new`로 만들면 매 전이가 할당을 발생시키고, 더 중요하게는 `StateMachine`의 중복 전이 가드가 무력화됩니다. 매번 다른 인스턴스라 `Current == next`가 성립하지 않기 때문입니다.

### 2.16 상태머신 재사용 — 동반자와 적

상태머신 베이스(`State`, `StateMachine`)를 먼저 설계한 뒤, **두 종류의 AI에 코드 수정 없이 재사용**했습니다.

| | 상태 | 소유 컴포넌트 |
|---|---|---|
| 동반자 | Idle ↔ Follow | `CompanionAI` |
| 적 | Patrol ↔ Chase ↔ Attack → Dead | `EnemyAI` |

적 AI를 추가하면서 `State`와 `StateMachine`은 한 줄도 수정하지 않았습니다. 추상화가 실제로 재사용 가능했는지에 대한 검증이 여기서 이루어졌습니다.

**상태가 공유하는 동작은 소유 컴포넌트에 둡니다.** 예를 들어 Patrol과 Chase는 목적지와 속도만 다를 뿐 이동 방식이 같으므로, `EnemyAI.MoveTowards(destination, speed)`로 공통화하고 각 상태는 "어디로, 얼마나 빨리"만 결정합니다.

**상태 고유의 데이터는 상태가 보관합니다.** 순찰 진행 인덱스는 `PatrolState`만 알면 되는 정보이므로 `EnemyAI`에 두지 않았습니다. 상태 객체를 재사용하는 구조이므로 Chase로 전이했다가 복귀해도 순찰 지점이 이어집니다.

### 2.17 체력 — 알림만 하고 판단하지 않음

`Health`는 플레이어와 적이 공유하는 컴포넌트입니다. 체력 변화에 반응해야 하는 대상이 여럿(체력 바 UI, 피격 연출, AI의 사망 처리, 게임 오버 판정)이므로, `Health`가 이들을 직접 호출하지 않고 **이벤트만 발행**합니다.

```csharp
public event Action<int, int> OnHealthChanged;   // (현재, 최대)
public event Action OnDied;
```

`EnemyAI`는 `OnDied`를 구독해 Dead 상태로 전이합니다. `Health`는 상태머신의 존재를 알지 못합니다.

이벤트를 둘로 나눈 이유는 관심사가 다르기 때문입니다. 하나로 합치면 구독자가 매번 사망 여부를 확인해야 합니다. 발행 순서는 `OnHealthChanged` → `OnDied`로 고정했습니다. 체력 바가 0까지 내려간 뒤 사망 연출이 시작되어야 자연스럽기 때문입니다.

방어 조건 두 가지를 두었습니다.

- `if (IsDead) return;` — 사망 후 추가 피격으로 `OnDied`가 중복 발행되는 것을 차단
- `if (amount <= 0) return;` — 음수 피해가 회복으로 동작하는 것을 차단

### 2.18 히스테리시스 — 상태 떨림 방지

전이 임계값을 하나로 두면 경계에서 상태가 매 프레임 진동합니다.

```
followDistance = 2.5   // 이보다 멀어지면 추적 시작
stopDistance   = 1.5   // 이보다 가까워지면 정지
```

두 값 사이에 간격을 두어, 한 번 추적을 시작하면 충분히 가까워질 때까지 유지되도록 했습니다. 온도조절기와 같은 원리입니다.

### 2.19 NavMesh 제거 — 요구사항에 맞는 도구 선택

동반자 이동을 처음에는 `NavMeshAgent`로 구현했습니다. 그러나 실제 요구사항을 다시 보면 **평면 지형에 우회할 장애물이 없었습니다.**

경로 탐색이 필요 없는 상황에서 NavMeshAgent의 회피·정지 로직이 계속 개입해, 목적지 설정과 정지 거리 사이에서 의도치 않은 선회가 발생했습니다. 정지 거리를 키우면 너무 멀리 서고, 줄이면 목적지가 플레이어 콜라이더 내부가 되어 도달 불가 상태로 선회했습니다. **두 조건을 동시에 만족하는 값이 존재하지 않는 구조**였습니다.

목표 지점을 향해 직접 이동하는 방식으로 교체했고, 코드가 짧아지고 동작이 예측 가능해졌습니다.

```csharp
if (distance > desiredDistance)
{
    Vector3 direction = toPlayer / distance;
    transform.position += direction * moveSpeed * Time.deltaTime;
    // 이동할 때만 회전
}
```

장애물이 있는 지형이 추가되면 NavMesh를 다시 도입하는 것이 맞습니다. **현재 요구사항에 비해 과한 도구를 유지하기 위해 시간을 쓰지 않기로** 판단했습니다.

### 2.20 UI — 데이터를 소유하지 않고 구독한다

UI 스크립트는 모두 같은 형태를 따릅니다.

```
OnEnable  → 데이터 소유자의 이벤트 구독
OnDisable → 해제
Start     → 현재 값으로 1회 갱신
핸들러    → 값이 바뀔 때만 화면 반영
```

**UI가 데이터를 들고 있지 않습니다.** 체력은 `Health`가, 아이템은 `PlayerInventory`가, 퀘스트 진행은 `QuestGiver`가 소유하고, UI는 표시만 합니다. 따라서 UI를 제거해도 게임 로직은 그대로 동작합니다.

**말하는 쪽과 표시하는 쪽 사이에는 창구를 두었습니다.**

| 창구 | 발행하는 쪽 | 구독하는 쪽 |
|---|---|---|
| `DialogueEvents` | `QuestGiver` 등 | `DialogueUI` |
| `QuestEvents` | `QuestGiver` | `QuestTrackerUI` |
| `Health.OnHealthChanged` | `Health` | 체력 바, 이름표 |
| `PlayerInventory.OnInventoryChanged` | 인벤토리 | 인벤토리 창, 퀘스트 트래커 |

`QuestGiver`는 대화창의 존재를 모르고, `DialogueUI`는 누가 말했는지 모릅니다.

**선택지는 콜백을 전달하는 방식으로 처리했습니다.** 퀘스트 수락/거절이 필요해지면서, "무엇을 할지"를 UI가 알 필요가 없도록 실행할 동작 자체를 넘깁니다.

```csharp
DialogueEvents.RequestChoice(speakerName, quest.acceptText,
    onAccept:  () => { /* 수락 시 동작 */ },
    onDecline: () => { /* 거절 시 동작 */ });
```

`DialogueUI`는 버튼이 눌리면 보관해 둔 동작을 실행할 뿐, 그 내용이 무엇인지 알지 못합니다.

**갱신은 변화가 있을 때만 수행합니다.** 예를 들어 상호작용 프롬프트는 대상이 바뀐 프레임에만 문자열을 갱신하고, 인벤토리 창은 열려 있을 때만 목록을 다시 만듭니다. 매 프레임 문자열을 조합하면 불필요한 할당이 누적됩니다.

### 2.21 클래스 분리 시점 — 지금은 나누지 않음

`PlayerController`는 현재 입력 읽기·이동·회전 세 가지를 담당합니다. 처음부터 `PlayerInputReader` / `PlayerMotor` / `PlayerController`로 분리하는 구조도 검토했지만, **현 시점에서는 나누지 않기로** 했습니다.

단일 책임 원칙은 "클래스당 기능 하나"가 아니라 **"바뀔 이유가 하나"**를 의미합니다. 현재 이 클래스는 이동 방식이 바뀔 때만 수정됩니다. 지금 나누면 파일 수와 상호 참조만 늘고 얻는 것이 없습니다.

대신 **분리 시점의 신호**를 미리 정해두었습니다.

- `Update`가 30줄을 초과할 때
- 상태를 확인하는 분기가 두세 개 이상 쌓일 때
- 새 기능을 어디에 넣을지 망설여질 때

전투를 추가하면 "공격 중 이동 제한", "넉백에 의한 외부 속도", "경직·사망 상태" 같은 요구가 생기므로 그 시점에 분리할 예정입니다.

## 4. AI 활용 기록

이 프로젝트는 생성형 AI를 개발 보조로 사용했습니다.
어디까지를 AI에 맡기고 어디부터 직접 판단했는지를 기록합니다.

### 작업 방식

코드를 먼저 받아 쓰는 대신, **직접 설계·작성한 뒤 AI에게 리뷰를 받는** 방식으로 진행했습니다.
문제를 만나면 먼저 스스로 접근 방식을 정리하고, 그 판단을 AI와 검증하는 순서를 지켰습니다.

### 직접 설계·판단한 부분

- 전체 아키텍처 구조와 시스템 간 통신 방식 (싱글톤 최소화 + 이벤트)
- 상호작용 판정 방식 선택 및 근거
- 이동 컴포넌트 선택 (CharacterController) 및 넉백 처리 방침
- 게임 상태 정의와 `SetState` 로직 작성
- 참조 주입 방식 기준 정립 (Inspector 주입 vs 런타임 캐싱)
- 클래스 분리 시점 판단 및 분리 신호 정의
- 스코프 결정 (전투 추가, "밀기" 제외)

### AI로 가속한 부분

- 작성한 코드에 대한 리뷰 및 개선점 확인
- 익숙하지 않은 API·에디터 동작 확인
- _(추가 예정)_

### AI 제안을 채택하지 않은 사례

| AI가 제안한 것 | 채택하지 않은 이유 | 실제로 택한 방식 |
|---|---|---|
| 제네릭 싱글톤 베이스 (`Singleton<T>`) | 현재 매니저가 GameManager 하나뿐. 하나 있는 상태에서 추상 클래스부터 만드는 것은 과설계. 두 번째 매니저가 생기는 시점이 추출 시점이라 판단 | 단일 클래스에 싱글톤 패턴 직접 구현 |
| ScriptableObject 기반 이벤트 시스템 | 유니티 진영에서 널리 쓰이는 패턴이지만, 현재 규모에서는 에셋 파일만 늘어나고 얻는 것이 적음 | C# `event Action` 사용 |
| 게임 전역 상태를 정식 상태머신으로 구현 | 상태머신은 "이 상태에서 저 상태로만 갈 수 있다"는 전이 제약이 있을 때 값어치가 있음. 게임 전역 상태는 어디서든 Paused로 갈 수 있어 제약이 거의 없음 | enum + `SetState` 단순 구조 (상태머신은 적·동반자 AI에만 적용) |
| 카메라 참조를 `[SerializeField]`로 Inspector 주입 | 프리팹이 씬 오브젝트 참조를 직렬화하지 못해, Player를 프리팹화하면 null이 됨. 할당 누락이 런타임에야 드러나는 문제도 있음 | `Awake`에서 1회 탐색 후 캐싱 + 실패 시 `Debug.LogError` |
| 처음부터 `PlayerInputReader`/`PlayerMotor`로 클래스 분리 | 현재 책임이 하나("이동")로 응집돼 있어 분리 이득이 없음. 파일 수와 상호 참조만 증가 | 단일 클래스 유지, 분리 신호를 사전에 정의해두고 전투 추가 시점에 분리 |
| 확장 가능한 스탯 시스템 (직업·레벨·능력치 계수) | 이 프로젝트의 캐릭터는 하나이고 실제로 사용되는 수치는 체력뿐. 쓰이지 않는 구조를 남기는 것은 확장성 고려가 아니라 스코프 판단 실패로 읽힘 | 플레이어·적이 공유하는 `Health` 컴포넌트만 구현 |

### 추상화 시점에 대한 기준

작업 중 반복적으로 "미리 일반화해둘까"라는 판단을 마주했고, 다음 기준을 세워 일관되게 적용했습니다.

> **두 번째 사례가 실제로 나타났을 때 추상화한다.**

- 매니저가 둘이 되면 → 싱글톤 베이스 추출
- 플레이어와 적이 모두 체력을 사용하면 → `Health` 컴포넌트로 공유 (해당됨)
- 캐릭터가 둘 이상이 되면 → 스탯 시스템 (이 프로젝트 범위에서는 발생하지 않음)

하나뿐인 상태에서 만드는 것은 추측이고, 둘이 된 뒤 만드는 것은 설계라고 판단했습니다.

### AI 조언 중 재검토한 사례

- 상태 전환 시 이벤트 발사 순서에 대해 처음 받은 조언(상태 갱신 → 이벤트 → timeScale)을, 구독자가 최종 상태를 보아야 한다는 이유로 **timeScale 적용을 이벤트보다 앞으로** 조정했습니다.

## 5. 어려웠던 점과 해결

### 문제 1: 퀘스트가 완료 상태로 전이되지 않음

- **상황**: 베리를 목표치만큼 모아도 NPC가 계속 "부족하다"고 응답. 상태는 `InProgress`에 고정.
- **원인 분석**: 완료 조건 분기에서 `questState = Completed`로 대입한 직후, 조건 밖에서 `questState = InProgress`를 무조건 재대입하고 있었습니다. 조건부 대입이 무조건 대입에 덮어써지는 구조였습니다.
- **해결**: 불필요한 재대입을 제거하고, 완료/미완료 처리를 `if/else`로 분리해 한쪽만 실행되도록 했습니다.
- **결과**: 정상 전이 확인. 이후 **"조건 안에서 바꾼 값을 조건 밖에서 다시 건드리지 않는다"**를 점검 항목으로 삼았습니다.

### 문제 2: 완료 조건이 즉시 충족되는 문제

- **상황**: 퀘스트 수락 직후 다시 말을 걸면 베리를 하나도 모으지 않았는데 완료 처리.
- **원인 분석**: 비교 연산자를 `>=`가 아닌 `<=`로 작성. `0 <= 3`이 참이 되어 첫 대화에서 완료 조건이 성립했습니다.
- **해결**: 부등호 방향 수정. 아울러 `==` 대신 `>=`를 사용해, 집계가 목표치를 초과하는 경우에도 조건이 성립하도록 했습니다.
- **결과**: 경계 조건은 정확한 일치보다 **범위로 판정**하는 편이 안전하다는 기준을 세웠습니다.

### 문제 3: 퀘스트 수락 전 획득분이 진행도에 반영되지 않음

- **상황**: 아이템을 먼저 3개 획득한 뒤 퀘스트를 수락하면, 소지 중임에도 진행도가 `0/3`으로 표시.
- **원인 분석**: 진행도를 수집 **이벤트 집계**로 구현했고, 집계 조건을 `QuestState.InProgress`로 제한하고 있었습니다. 조건을 제거하면 반대로 아이템을 소비한 뒤에도 집계가 남는 문제가 생겨, 조건 조정만으로는 해결되지 않았습니다.
- **해결**: 판정 근거를 사건 집계에서 **인벤토리 상태 조회**로 전환했습니다(2.13 참조).
- **결과**: 획득 시점과 순서에 무관하게 동작합니다. 아울러 **"사건을 세지 말고 상태를 물어본다"**를 조건 판정의 기본 방침으로 삼았습니다.

### 문제 4: 동반자가 플레이어 주위를 계속 선회함

가장 오래 붙잡힌 문제였고, **원인이 두 겹으로 겹쳐 있어** 증상만으로는 구분이 되지 않았습니다.

- **상황**: 동반자가 플레이어를 따라오지 않거나, 따라오더라도 주위를 빙빙 돌았습니다. 가까이 다가가면 더 심해졌습니다.

- **진단 과정**: 추측으로 파라미터를 조정하는 대신, 단계적으로 로그를 좁혀 나갔습니다.
  1. 상태 전이 로그 → 전이는 정상
  2. `isOnNavMesh` / `pathStatus` / `remainingDistance` → 경로는 유효한데 `remaining=0`
  3. `position` / `target` / `destination` 비교 → **목적지가 자기 위치와 동일**
  4. Idle 상태에서 `position`과 `distance` 로그 → **플레이어가 접근하는데 거리가 증가**

- **원인 1 — 계층 구조의 위치 오프셋**: 로직은 부모 오브젝트를 이동시키는데, 실제로 보이는 모델은 자식이었고 자식의 로컬 위치가 원점이 아니었습니다. **눈에 보이는 위치와 계산되는 위치가 서로 달랐습니다.** 부모가 회전하면 오프셋된 자식이 부모를 중심으로 궤도를 그리므로, 이것이 "선회"의 실체였습니다.

- **원인 2 — 근거리에서의 방향 벡터 불안정**: 대상과 가까워질수록 방향 벡터의 크기가 작아져, 미세한 위치 변화에도 정규화 결과가 크게 흔들립니다. 매 프레임 이 값으로 목표 회전을 갱신하면 회전이 진동합니다.

- **해결**:
  1. 자식 오브젝트의 로컬 위치를 원점으로 정렬. 자식은 크기·정면 축 보정만 담당하도록 역할을 분리했습니다.
  2. 회전 갱신을 **실제로 이동하는 경우로 한정**했습니다. 정지 상태에서는 방향을 계산하지 않으므로 진동이 발생할 수 없습니다.

  ```csharp
  if (distance > desiredDistance)   // 이 안에서만 이동과 회전을 수행
  ```

- **결과**: 로그로 범위를 좁히는 방식이 결정적이었습니다. "보이는 것"이 아니라 **"계산되는 값"을 직접 확인**해야 원인이 드러난다는 점, 그리고 증상 하나에 원인이 둘 이상일 수 있다는 점을 확인했습니다.

### 문제 5: 적 접근 시 캐릭터가 진동하고 공격이 발생하지 않음

- **상황**: 적이 사거리에 들어오면 플레이어가 미세하게 떨리고, 그 상태로 적이 공격을 전혀 하지 않았습니다.

- **원인 분석**: 두 증상의 원인이 하나였습니다. 적은 `transform.position`을 직접 갱신해 충돌을 고려하지 않고 전진하는데, 플레이어의 `CharacterController`는 겹친 콜라이더에서 자신을 밀어냅니다. 매 프레임 서로 밀고 밀리며 **대상 간 거리가 진동**했습니다.
  그 진동이 `attackRange`(진입)와 `attackExitRange`(이탈) 경계를 계속 넘나들어 Attack ↔ Chase 전이가 반복되었고, `AttackState.Enter()`에서 공격 쿨다운 기준 시각이 매번 초기화되어 **쿨다운이 영원히 충족되지 않았습니다.**

- **해결**: 적 콜라이더를 트리거로 전환해 물리적 밀어냄을 제거했습니다. 트리거는 이동을 막지 않지만 `Physics.OverlapSphere` 질의에는 여전히 검출되므로, 양쪽의 공격 판정은 그대로 동작합니다.
  아울러 진입/이탈 임계값을 분리(`attackRange` < `attackExitRange`)해 경계에서의 전이 진동을 구조적으로도 차단했습니다.

- **결과**: 물리적 상호작용이 상태 전이에 간섭할 수 있다는 점, 그리고 **표면적으로 다른 두 증상이 하나의 원인에서 나올 수 있다**는 점을 확인했습니다. 동반자 선회 문제(문제 4)와 함께, 임계값을 하나로 두면 경계에서 반드시 진동이 발생한다는 교훈이 반복되었습니다.

### 문제 6: UI 초기 표시가 0으로 나타남

- **상황**: 플레이어 체력이 100인데 체력 바에는 `0 / 100`으로 표시. 피해를 입은 뒤에는 `90 / 100`처럼 정상 표시.
- **원인 분석**: UI가 `OnEnable`에서 `Health.Current`를 읽는데, 그 시점에 `Health.Awake()`가 아직 실행되지 않아 `Current`가 int 기본값 0이었습니다. `Max`는 직렬화된 필드라 정상값이 읽혀 "0 / 100"이라는 조합이 나왔습니다. **오브젝트 간 `Awake` 호출 순서는 보장되지 않습니다.**
- **해결**: 구독은 `OnEnable`에 두되, **초기 표시만 `Start()`로 이동**했습니다. `Start`는 모든 `Awake` 이후에 실행됩니다.
- **결과**: 실행 순서를 강제(`DefaultExecutionOrder`)하기보다 **순서에 의존하지 않는 위치로 옮기는 편**이 견고하다고 판단했습니다. "이벤트가 오지 않는" 문제가 아니라 "구독은 되었으나 초기값을 잘못 읽은" 문제였다는 점에서 원인 파악이 까다로웠습니다.

### 문제 7: 계층 구조에서 로컬 좌표가 초기화되지 않음 (재발)

- **상황**: 캐릭터 머리 위에 표시할 이름표를 배치했으나 화면에 보이지 않음.
- **원인 분석**: 프리팹을 부모 아래로 드래그할 때 월드 위치가 유지되어, 로컬 좌표가 `(2.67, -3.62, -8.18)`로 남아 있었습니다. 이름표가 캐릭터 모델 내부에 위치해 메시에 가려진 상태였습니다.
- **해결**: 자식의 로컬 좌표를 원점으로 정렬하고, 높이는 부모(앵커)에서 조정하도록 역할을 분리했습니다.
- **결과**: **동반자 선회 문제(문제 4)와 동일한 원인이 다른 형태로 재발**했습니다. 이후 계층 구조에 오브젝트를 배치할 때 로컬 좌표 확인을 고정 점검 항목으로 삼았습니다.

### 문제 8: 상호작용 대상 선택이 플레이어 의도와 어긋남

- **상황**: 베리가 인접해 있을 때, 바라보는 대상이 아니라 뒤쪽의 더 가까운 대상이 선택되는 경우 발생.
- **원인 분석**: 거리만으로 순위를 매기면 플레이어의 조작 의도(바라보는 방향)가 반영되지 않습니다. 식물을 심어 군집이 형성되는 이 게임에서는 빈번히 발생할 수 있는 상황이었습니다.
- **해결**: 정면성(내적)을 **필터**로, 거리를 **순위 기준**으로 분리했습니다. 두 값을 가중합으로 섞는 방안도 검토했으나, 가중치 근거를 설명하기 어렵고 튜닝이 감각에 의존하게 되어 채택하지 않았습니다.
- **결과**: "앞쪽에 있는 것 중 가장 가까운 것"이라는 한 문장으로 규칙을 설명할 수 있게 되었습니다.
