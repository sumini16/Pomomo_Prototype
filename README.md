# Pomomo Prototype

판타지 RPG의 도입부 한 구간을 구현한 Unity 프로토타입입니다.
마을 사람의 부탁으로 딸기를 모으고, 사냥꾼의 의뢰로 슬라임을 처치한 뒤,
열린 길을 따라 르발을 만나는 지점에서 끝납니다.

완성된 게임을 목표로 하지 않았습니다. 기능을 넓게 늘어놓는 대신,
몇 개의 시스템을 **왜 그렇게 만들었는지 설명할 수 있는 수준**까지 만드는 쪽을 택했습니다.
이 문서의 절반 이상이 "무엇을 만들었나"가 아니라 "왜 그렇게 정했나"인 것도 그 때문입니다.

**개발 기간** 2026.08.25 ~ 2026.09.06 (13일)
**환경** Unity 6 (6000.5.9f1) · URP 17.5 · Input System 1.20 · Cinemachine 3.1
**플레이 영상** https://www.youtube.com/watch?v=39XX1OEO-W4

핵심 구현

• 이벤트 기반 시스템 간 통신
• ScriptableObject 기반 데이터/런타임 상태 분리
• 다형성 기반 Interaction
• 재사용 가능한 StateMachine
• Dictionary 기반 Inventory
• 상태 조회 기반 Quest Objective
• JSON Save/Load 및 GameDatabase
• 실제 디버깅 사례 11건

## 플레이 흐름

```
직업 선택 (전사 / 기사 / 마법사)
   ↓
마을 사람  →  정원의 딸기 3개 모으기          수집형 목표
사냥꾼     →  슬라임 처치                     처치형 목표  → 골드 보상
상점       →  물약·케이크 구매 / 딸기 판매     골드 ↔ 인벤토리
르발       →  만나기                          대화형 목표 (슬라임을 잡아야 열림)
   ↓
서쪽 성으로 — 프로토타입 종료
```

세 종류의 목표는 완료 판정 방식이 전부 다릅니다.
소지 여부를 조회하고, 처치 횟수를 세고, 대화 플래그를 확인합니다.
그런데 이걸 호출하는 `QuestGiver`는 셋을 구분하지 않습니다. 코드 한 줄로 처리합니다.

### 의도적으로 넣지 않은 것

적 여러 종, 원거리 공격, 콤보, 회피·패링, 드랍 테이블, 레벨업.

**성장형 오브젝트(작물 재배)** 는 만들려다 접었습니다. 타이머와 상태 전이로 구성되는데,
상태머신은 이미 동반자와 적 AI에서 두 번 썼습니다. 세 번째로 같은 걸 보여주는 것보다
아직 안 다룬 영역(퀘스트 목표 추상화, 상점·골드)을 채우는 게 낫다고 봤습니다.

**오브젝트 풀링**도 뺐습니다. 이 프로토타입에서 반복 생성·파괴되는 건 적 세 마리와 아이템 여섯 개입니다.
풀링을 넣어도 프레임 차이가 측정되지 않습니다. 숫자로 뒷받침 못 하는 걸 "성능 개선"이라고 쓰긴 어렵습니다.

## 2. 설계 기록

### 2.1 상호작용 판정: 레이캐스트를 쓰지 않은 이유

처음엔 레이캐스트를 생각했습니다. 전에 아이템 줍기를 만들 때 그렇게 했으니까요.

그런데 그때는 조준점이 있는 1인칭이었습니다. 이건 3인칭 탐험 게임입니다.
조준점이 없으니 판정이 어디로 나가는지 플레이어가 감을 못 잡고,
딸기처럼 작은 물체는 얇은 레이 하나로 자주 빗나갑니다.

그래서 주변 반경의 후보를 `Physics.OverlapSphere`로 모은 다음,
거리와 정면 여부로 점수를 매겨 하나를 고르는 방식으로 갔습니다.

```csharp
Vector3 toTarget = (target.position - transform.position).normalized;
float facing = Vector3.Dot(transform.forward, toTarget); // 1=정면, 0=옆, -1=뒤
```

정면성은 필터로, 거리는 순위 기준으로 나눠서 씁니다.
두 값을 가중합으로 섞는 안도 검토했는데, 가중치의 근거를 설명할 수가 없어서 접었습니다.
지금 방식은 "앞에 있는 것 중 가장 가까운 것"이라고 한 문장으로 설명됩니다.

### 2.2 이동은 CharacterController로

Rigidbody도 후보였습니다. 상호작용이 많으니 물리 기반이 낫지 않을까 싶었거든요.
따져보니 남은 상호작용(줍기·대화)에 플레이어 쪽 물리가 필요 없었습니다.

|  | CharacterController | Rigidbody |
|---|---|---|
| 넉백 | 직접 구현 (약 4줄) | `AddForce` 한 줄 |
| 평소 이동 | 정확하고 예측 가능 | 경사 미끄러짐, 벽 떨림 |
| 튜닝 | 속도 값 위주 | mass/drag/friction 조합 |
| 코드 구조 | Update 하나 | 입력 Update / 이동 FixedUpdate 분리 |

Rigidbody는 넉백 하나를 쉽게 만드는 대신 나머지 전부를 어렵게 만듭니다.
넉백은 속도 변수를 두고 `Lerp`로 감쇠시키는 방식으로 직접 넣었습니다.

### 2.3 싱글톤은 하나만

매니저마다 싱글톤을 두는 구조를 먼저 떠올렸는데,
그러면 매니저끼리 직접 참조하게 되고 초기화 순서에 의존하게 됩니다.

GameManager만 싱글톤으로 두고 나머지는 이벤트로 통신합니다.
`[DefaultExecutionOrder(-100)]`을 붙여, 다른 스크립트가 `Awake`에서 `Instance`를 써도
초기화가 먼저 끝나 있도록 했습니다. 유니티는 `Awake` 호출 순서를 보장하지 않습니다.

상태 전환은 **상태 갱신 → timeScale 적용 → 이벤트 발사** 순서를 지킵니다.
구독자가 이벤트를 받는 시점엔 세상이 이미 최종 상태여야 합니다.
순서가 뒤집히면 핸들러 안에서 옛 값을 읽게 되고, 이런 버그는 나중에 원인을 못 찾습니다.

이벤트는 `Action<GameState, GameState>`로 이전 상태와 새 상태를 함께 넘깁니다.
구독자가 "어디서 왔는지"를 알아야 하는 경우가 자주 생기는데,
나중에 파라미터를 추가하려면 모든 구독자를 고쳐야 하니 처음부터 넣었습니다.

### 2.4 카메라는 회전시키지 않기로 했다

처음엔 카메라를 플레이어의 자식으로 뒀습니다.
그랬더니 캐릭터가 이동 방향으로 회전할 때 카메라가 같이 돌아서 방향 감각이 무너졌습니다.
탐험 게임에서는 치명적입니다.

마우스로 카메라를 돌리는 3인칭 방식도 검토했지만, **각도를 고정한 쿼터뷰**로 갔습니다.
로스트아크 같은 쿼터뷰 액션 RPG가 참고 대상이었습니다.

- 화면의 위쪽이 항상 같은 월드 방향이라 길을 잃지 않습니다
- 조작할 게 하나 줄어듭니다. 마우스는 공격과 UI에만 씁니다
- 카메라가 벽에 파묻히는 상황 자체가 생기지 않습니다

구현은 Cinemachine의 `CinemachineFollow` 하나입니다.
플레이어를 고정 오프셋으로 따라가고 회전은 하지 않습니다.
댐핑이 기본으로 들어 있어 캐릭터가 급하게 움직여도 카메라가 부드럽게 따라옵니다.

직접 만들어도 되는 수준이긴 하지만, 이 프로젝트에서 보여주려는 건 카메라 수학이 아니라
게임 시스템 설계입니다. 검증된 패키지에 맡기고 그 시간을 다른 데 쓰는 게 낫다고 봤습니다.

### 2.5 카메라 기준 이동

카메라를 고정했다고 월드 기준 이동을 그대로 쓸 수는 없었습니다.
카메라가 비스듬히 내려다보는 각도라, `W`를 눌러 월드 +Z로 가면
화면에서는 대각선으로 걷는 것처럼 보입니다.

그래서 입력을 카메라 기준으로 변환합니다.
플레이어가 기대하는 건 "월드의 어느 축"이 아니라 "화면에서 위쪽"이기 때문입니다.

```csharp
Vector3 camForward = cameraTransform.forward;
Vector3 camRight   = cameraTransform.right;
camForward.y = 0f;   // 카메라가 아래를 내려다보므로 y 성분 제거
camRight.y   = 0f;
camForward.Normalize();   // y를 뺀 만큼 짧아진 길이를 1로 복원
camRight.Normalize();

Vector3 direction = camForward * moveInput.y + camRight * moveInput.x;
```

`Normalize()`를 빼먹으면 실제 이동 속도가 `moveSpeed`보다 느려집니다.
y를 잘라낸 벡터는 길이가 1보다 짧은데, 그걸 그대로 속도에 곱하기 때문입니다.
카메라 각도를 나중에 조정하면 그만큼 속도가 또 달라져서, 원인을 찾기 어려운 종류의 버그가 됩니다.

정규화 조건도 신경 썼습니다. 대각선 입력이 1을 넘을 때만 정규화합니다.
무조건 정규화하면 게임패드 스틱을 살짝(0.3쯤) 밀었을 때 값이 1로 늘어나
미세한 속도 조절이 불가능해집니다.

회전은 `Quaternion.LookRotation`으로 목표를 구한 뒤 `Slerp`로 보간합니다.
목표값을 바로 대입하면 방향 전환이 뚝뚝 끊깁니다.
입력이 없을 때(0벡터)는 `LookRotation`이 경고를 뱉으므로 조기 반환으로 걸러냅니다.

### 2.6 참조를 어떻게 넣을 것인가

카메라 참조를 `[SerializeField]`로 인스펙터에서 넣으려다 두 가지에 걸렸습니다.
할당을 빠뜨려도 컴파일 때는 아무 말이 없고 런타임에 null이 됩니다.
그리고 **프리팹은 씬 오브젝트 참조를 직렬화하지 못합니다.**
Player를 프리팹으로 만들면 씬의 카메라를 가리키던 참조가 인스턴스화 시점에 null이 됩니다.

기준을 나눠서 정했습니다.

| 방식 | 적용 대상 |
|---|---|
| `[SerializeField]` 주입 | 같은 프리팹·계층 안의 참조 (자식 모델, 손 슬롯, 이펙트) |
| `Awake`에서 1회 탐색 후 캐싱 | 씬에 하나뿐인 전역 대상 (메인 카메라, 매니저) |

탐색에 실패하면 `Debug.LogError`로 이유를 남깁니다.
그냥 두면 한참 뒤 이동 로직에서 맥락 없는 `NullReferenceException`이 터져서 원인을 못 찾습니다.

### 2.7 상호작용은 다형성으로, 알림은 이벤트로

대상마다 하는 일이 다릅니다. 딸기는 줍고 NPC는 말합니다.
`PlayerInteractor`가 종류를 판별해서 분기하면 대상이 늘 때마다 `PlayerInteractor`를 고쳐야 합니다.

`Interactable` 추상 클래스에 `Interact()`를 두고 각자 구현하게 했습니다.
`PlayerInteractor`는 이 한 줄만 실행합니다.

```csharp
target.Interact(gameObject);   // 무슨 일이 일어나는지 모름
```

지금 `ItemPickup`, `QuestGiver`, `ShopNpc`, `DialogueNpc` 네 종류가 이 구조 위에 있습니다.
넷을 다 만드는 동안 `PlayerInteractor`는 한 줄도 안 바뀌었습니다.

**이벤트를 쓴 자리는 따로 있습니다.** 처음엔 상호작용 자체를 이벤트로 처리할까 했는데,
두 방식이 답하는 질문이 다르다는 걸 정리하고 나서 갈렸습니다.

| | 답하는 질문 |
|---|---|
| 다형성 | 이 대상이 **무엇을 할 것인가** (일대일 위임) |
| 이벤트 | 이 일이 일어났음을 **누가 알아야 하는가** (일대다 알림) |

덧붙이면 C#의 `event`는 선언한 클래스 밖에서 `Invoke`할 수 없어서
상호작용 실행에는 애초에 맞지 않았습니다.

### 2.8 아이템은 코드가 아니라 데이터로

처음엔 아이템 종류마다 스크립트를 만들었습니다. `BerryPickup`, `PotionPickup`, …
쓰다 보니 **줍는 동작은 전부 같고 다른 건 데이터뿐**이라는 게 드러났습니다.
종류가 늘 때마다 코드가 늘어나는 구조였습니다.

`ItemData`(ScriptableObject)로 정보를 빼고, 동작은 `ItemPickup` 하나로 합쳤습니다.

```
스크립트 1개 (ItemPickup) + 데이터 에셋 N개 (Item_Berry, Item_Cake, …)
```

새 아이템을 넣을 때 코드를 안 써도 됩니다. 에셋 만들고 프리팹에 할당하면 끝입니다.

**식별은 문자열이 아니라 참조로 합니다.**

```csharp
if (collected != targetItem) return;   // 에셋 참조 비교
```

`displayName == "딸기"` 같은 문자열 비교는 표시 이름을 바꾸는 순간
컴파일 오류 없이 조용히 깨집니다. 에셋 참조는 이름을 바꿔도 그대로입니다.

열거형도 `questState <= QuestState.InProgress` 같은 순서 의존 비교를 피하고 `==`만 씁니다.
선언 순서가 바뀌면 조건의 의미가 경고 없이 달라지기 때문입니다.

> 참고로 ScriptableObject 기반 이벤트 시스템은 채택하지 않았는데(4장 참조) 아이템 데이터에는 썼습니다.
> 같은 도구라도 **실제로 있는 문제를 푸는가**가 기준이었습니다.
> 전자는 C# 이벤트로 이미 해결되는 문제였고, 후자는 데이터 중복이라는 실재하는 문제가 있었습니다.

### 2.9 인벤토리 자료구조

인벤토리에서 제일 자주 하는 연산은 "이 아이템 몇 개 있나" 조회입니다.
퀘스트 조건 판정도, UI 표시도, 상점 판매 가능 여부도 전부 이걸 묻습니다.

| 후보 | 개수 조회 | 비고 |
|---|---|---|
| `List<ItemData>` | O(n) | 획득 순서는 보존됨 |
| 슬롯 배열 | O(n) | 격자 UI에 맞지만 빈 칸 관리 필요 |
| `Dictionary<ItemData, int>` | **O(1)** | 종류별 집계에 직결 |

지배적 연산이 조회라서 Dictionary로 갔습니다.

구현하면서 두 군데 걸렸습니다.
`items[key]` 직접 접근은 없는 키에서 `KeyNotFoundException`이 나므로 조회는 `TryGetValue`로 합니다.
그리고 수량이 0이 되면 키 자체를 지웁니다. 안 지우면 `Item_Berry → 0` 같은 항목이 쌓여서
UI를 순회할 때 빈 칸으로 튀어나옵니다.

격자 UI는 이 Dictionary를 그대로 쓰지 않고, 표시할 때만 리스트로 펼칩니다.
데이터 구조는 조회에 맞추고 표현은 표현대로 하자는 판단이었습니다.

### 2.10 사건을 세지 말고 상태를 물어보기

퀘스트 진행도를 처음엔 수집 **이벤트 집계**로 만들었습니다. `collectedCount++`.
테스트하다 이게 나왔습니다.

> 퀘스트를 받기 전에 딸기를 먼저 주우면, 가방에 있는데도 진행도가 0으로 나옴.

집계 조건을 풀면 반대 문제가 생깁니다. 아이템을 팔거나 써도 집계는 남아서
아이템 없이 퀘스트가 완료됩니다.

원인은 **사건을 세고 있었다는 것**이었습니다.
사건 집계는 하나만 놓쳐도 복구가 안 되고, 순서에 민감하고, 되돌릴 수 없습니다.

인벤토리를 넣은 뒤 상태 조회로 바꿨습니다.

```csharp
int count = inventory.GetCount(quest.targetItem);   // 묻는 시점의 사실만 확인
```

언제 주웠는지, 몇 번에 나눠 모았는지가 조건에 영향을 안 줍니다. 쓰면 조건이 자연히 깨집니다.
바꾸고 나니 `QuestGiver`에서 필드 하나, 메서드 하나, 구독·해제 두 줄이 사라져서
**코드가 오히려 짧아졌습니다.**

### 2.11 설정 데이터와 런타임 상태를 갈라놓기

퀘스트 정보를 `QuestData`(ScriptableObject)로 뺐지만
진행 상태(`QuestState`)는 거기 두지 않았습니다.

ScriptableObject에 런타임 상태를 저장하면 에셋 자체의 데이터와 런타임 상태가 섞이고, 같은 에셋을 참조하는 객체 사이에서 상태가 공유될 수 있습니다.
에디터에서는 플레이를 멈춰도 값이 안 돌아가서, 다음 실행이 이미 완료된 상태로 시작됩니다.
같은 에셋을 쓰는 인스턴스가 여럿이면 상태를 공유해버리기도 합니다.

| 성격 | 위치 | 예 |
|---|---|---|
| 설정 (불변) | ScriptableObject | 대사, 목표 아이템, 필요 수량, 적 스탯 |
| 상태 (가변) | MonoBehaviour | 퀘스트 진행도, 현재 체력, 소지 골드 |

이 기준을 적 스탯에도 그대로 적용했습니다.
처음엔 `EnemyAI`가 이동 속도·탐지 거리·공격력을 직접 `[SerializeField]`로 들고 있었는데,
적을 여러 마리 놓자 값 하나 바꿀 때마다 오브젝트를 전부 고쳐야 했고
어느 게 기준값인지 알 수 없어졌습니다.

수치를 `EnemyData`로 옮기고 **`EnemyAI`에는 숫자 필드를 하나도 안 남겼습니다.**
개체마다 달라야 하는 순찰 지점만 컴포넌트에 남습니다.

`EnemyData.OnValidate()`에서 `loseRange > detectRange`와 `attackExitRange > attackRange`를 강제합니다.
2.14에서 만든 히스테리시스는 두 임계값의 대소 관계가 지켜져야만 성립하는데,
이건 코드가 아니라 **데이터 입력에서 깨질 수 있는 조건**입니다. 그래서 에디터 단계에서 막았습니다.

### 2.12 직업: 캐릭터를 늘리지 않고 데이터를 늘리기

전사·기사·마법사 세 직업이 있습니다.
직업마다 프리팹을 따로 만드는 방법도 있었지만, 실제로 다른 건 수치와 손에 든 물건뿐이었습니다.

`ClassData`(ScriptableObject)에 체력·공격력·이동속도·방어력·무기·보조장비·시작 아이템을 넣고,
`PlayerClassApplier`가 `Awake`에서 그걸 읽어 각 컴포넌트에 주입합니다.

```
Health.SetMaxHealth / SetDefense
PlayerCombat.SetAttackDamage
PlayerController.SetMoveSpeed
손 슬롯에 weaponPrefab / offhandPrefab 생성
inventory.Add(starterItem)
```

| | 체력 | 공격력 | 이동속도 | 방어력 | 장비 |
|---|---|---|---|---|---|
| 전사 | 120 | 20 | 5.5 | 0 | 한손검 + 방패 |
| 기사 | 180 | 10 | 4.0 | 5 | 도끼 + 방패 |
| 마법사 | 80 | 30 | 5.0 | 0 | 지팡이 |

직업이 하나 더 늘어도 코드는 안 바뀝니다. 에셋 하나와 카드 프리팹 하나면 됩니다.

방어력은 `Health.TakeDamage` 안에서 감산합니다.
다만 `Mathf.Max(1, amount - defense)`로 최소 1은 들어가게 했습니다.
0이 되면 어떤 공격으로도 안 죽는 교착 상태가 생깁니다.

선택값은 `GameManager`가 들고 `DontDestroyOnLoad`로 본 씬까지 넘깁니다.
살아남는 객체가 씬 오브젝트를 캐싱하지 않는다는 규칙(2.3)이 여기서 값을 합니다.

### 2.13 상태머신을 먼저 만들고 두 곳에 재사용

동반자와 적은 행동은 다르지만 **상태를 갖고 전이한다**는 골격이 같습니다.
그래서 상태머신을 먼저 설계하고 양쪽에 붙이는 순서로 갔습니다.

```csharp
public abstract class State
{
    public virtual void Enter() { }
    public virtual void Tick()  { }
    public virtual void Exit()  { }
}
```

**enum + switch로 안 한 이유는 `Enter`/`Exit` 때문입니다.**
상태에 들어가는 순간 한 번만 해야 할 일(애니메이션 시작, 목적지 설정)과
나올 때 한 번만 해야 할 일(정리)이 있는데,
switch에서는 "지금 막 진입했는가"를 판별할 방법이 없어 플래그를 계속 들고 다녀야 합니다.
상태가 늘수록 그 뒷정리가 분기문을 뒤덮습니다.

**전이 판단은 각 상태가 스스로 합니다.** `CompanionAI`는 거리 조건을 모릅니다.
각 상태의 `Tick`이 조건을 확인해서 전이를 요청합니다.
상태를 추가해도 `CompanionAI`는 안 바뀝니다. 2.7과 같은 구조입니다.

**상태 객체는 `Awake`에서 한 번 만들고 재사용합니다.**
전이할 때마다 `new`로 만들면 매 전이가 할당을 일으키고,
더 중요하게는 `StateMachine`의 중복 전이 가드가 무력해집니다.
매번 다른 인스턴스라 `Current == next`가 성립할 수 없기 때문입니다.

| | 상태 | 소유 컴포넌트 |
|---|---|---|
| 동반자 | Idle ↔ Follow | `CompanionAI` |
| 적 | Patrol ↔ Chase ↔ Attack → Dead | `EnemyAI` |

적 AI를 붙이면서 `State`와 `StateMachine`은 한 줄도 안 고쳤습니다.
추상화가 실제로 재사용되는지에 대한 검증이 여기서 됐습니다.

공통 동작은 소유 컴포넌트에 둡니다.
Patrol과 Chase는 목적지와 속도만 다르고 이동 방식이 같으므로
`EnemyAI.MoveTowards(destination, speed)`로 묶고 각 상태는 "어디로, 얼마나 빨리"만 정합니다.

반대로 상태 고유의 데이터는 상태가 갖습니다.
순찰 진행 인덱스는 `PatrolState`만 알면 되는 정보라 `EnemyAI`에 두지 않았습니다.
상태 객체를 재사용하니 Chase로 갔다 돌아와도 순찰 지점이 이어집니다.

### 2.14 히스테리시스

전이 임계값을 하나로 두면 경계에서 상태가 매 프레임 진동합니다.

```
followDistance = 2.5   // 이보다 멀어지면 추적 시작
stopDistance   = 1.5   // 이보다 가까워지면 정지
```

두 값 사이에 간격을 두어, 한 번 추적을 시작하면 충분히 가까워질 때까지 유지되게 했습니다.
온도조절기와 같은 원리입니다. 적의 `detectRange`/`loseRange`,
`attackRange`/`attackExitRange`도 같은 방식입니다.

### 2.15 체력은 알리기만 하고 판단하지 않는다

`Health`는 플레이어와 적이 함께 쓰는 컴포넌트입니다.
체력 변화에 반응해야 하는 쪽이 여럿이라(체력 바, 이름표, 피격 연출, AI 사망 처리)
`Health`가 이들을 직접 부르지 않고 이벤트만 발행합니다.

```csharp
public event Action<int, int> OnHealthChanged;   // (현재, 최대)
public event Action OnDied;
```

`EnemyAI`는 `OnDied`를 구독해 Dead로 전이합니다. `Health`는 상태머신의 존재를 모릅니다.

이벤트를 둘로 나눈 건 관심사가 다르기 때문입니다.
하나로 합치면 구독자가 매번 사망 여부를 확인해야 합니다.
발행 순서는 `OnHealthChanged` → `OnDied`로 고정했습니다.
체력 바가 0까지 내려간 다음에 사망 연출이 시작되어야 자연스럽습니다.

방어 조건 두 개를 넣었습니다.
`if (IsDead) return;` — 죽은 뒤 추가 피격으로 `OnDied`가 두 번 나가는 걸 막습니다.
`if (amount <= 0) return;` — 음수 피해가 회복으로 동작하는 걸 막습니다.

### 2.16 NavMesh를 걷어낸 이유

동반자 이동을 처음엔 `NavMeshAgent`로 만들었습니다.
그런데 실제 요구사항을 다시 보니 **평면 지형에 우회할 장애물이 없었습니다.**

경로 탐색이 필요 없는 상황에서 NavMeshAgent의 회피·정지 로직이 계속 끼어들어,
목적지 설정과 정지 거리 사이에서 의도치 않은 선회가 났습니다.
정지 거리를 키우면 너무 멀리 서고, 줄이면 목적지가 플레이어 콜라이더 안쪽이 되어
도달 불가 상태로 빙빙 돕니다. **두 조건을 동시에 만족하는 값이 없는 구조**였습니다.

목표 지점으로 직접 이동하는 방식으로 바꾸니 코드가 짧아지고 동작이 예측 가능해졌습니다.

```csharp
if (distance > desiredDistance)
{
    Vector3 direction = toPlayer / distance;
    transform.position += direction * moveSpeed * Time.deltaTime;
    // 이동할 때만 회전
}
```

장애물이 있는 지형이 생기면 NavMesh를 다시 넣는 게 맞습니다.
지금 요구사항에 비해 과한 도구를 유지하려고 시간을 쓰지 않기로 했습니다.

### 2.17 UI는 데이터를 갖지 않는다

UI 스크립트는 전부 같은 모양입니다.

```
OnEnable  → 데이터 소유자의 이벤트 구독
Start     → 현재 값으로 1회 갱신
핸들러    → 값이 바뀔 때만 화면 반영
OnDisable → 구독 해제
```

체력은 `Health`가, 아이템은 `PlayerInventory`가, 퀘스트는 `QuestLog`가 갖고 UI는 표시만 합니다.
UI를 통째로 지워도 게임 로직은 그대로 돕니다.

말하는 쪽과 표시하는 쪽 사이에는 창구를 뒀습니다.

| 창구 | 발행 | 구독 |
|---|---|---|
| `DialogueEvents` | `QuestGiver`, `DialogueNpc` | `DialogueUI` |
| `QuestEvents` | `QuestGiver` | `QuestTrackerUI`, `EndingUI` |
| `Health.OnHealthChanged` | `Health` | 체력 바, 이름표 |
| `PlayerInventory.OnInventoryChanged` | 인벤토리 | 인벤토리 창, 퀘스트 트래커 |
| `Wallet.OnGoldChanged` | 지갑 | 골드 HUD, 상점 |

`QuestGiver`는 대화창의 존재를 모르고, `DialogueUI`는 누가 말했는지 모릅니다.

**선택지는 콜백을 넘기는 방식으로 처리했습니다.**
퀘스트 수락/거절이 필요해지면서, "무엇을 할지"를 UI가 알 필요 없게 동작 자체를 넘깁니다.

```csharp
DialogueEvents.RequestChoice(speakerName, quest.acceptText,
    onAccept:  () => { /* 수락 시 동작 */ },
    onDecline: () => { /* 거절 시 동작 */ });
```

`DialogueUI`는 버튼이 눌리면 보관해 둔 동작을 실행할 뿐, 그 내용은 모릅니다.

갱신은 변화가 있을 때만 합니다.
상호작용 프롬프트는 대상이 바뀐 프레임에만 문자열을 만들고,
인벤토리 창은 열려 있을 때만 목록을 다시 짭니다.
매 프레임 문자열을 조합하면 불필요한 할당이 쌓입니다.

같은 이유로 `PlayerCombat`의 공격 판정은 `OverlapSphereNonAlloc`에 미리 잡아둔
`Collider[16]` 버퍼를 넘겨서, 공격할 때마다 배열이 새로 생기지 않게 했습니다.

### 2.18 UI 입력 차단: 서로를 모르게

상점이나 인벤토리가 열려 있는 동안 플레이어가 움직이거나 공격하면 안 됩니다.
UI가 `PlayerController.enabled = false`로 직접 끄는 게 제일 짧지만,
그러면 UI가 플레이어를 알아야 하고 UI가 늘수록 누가 껐는지·언제 켜야 하는지가 흩어집니다.

`UIState`라는 정적 창구를 하나 두고, UI는 열고 닫을 때 `SetModal(true/false)`만 부릅니다.
플레이어 쪽 스크립트는 `UIState.IsModalOpen`을 보고 **스스로** 입력을 무시합니다.
양쪽이 서로를 참조하지 않으니 UI를 새로 추가해도 플레이어 코드는 안 바뀝니다.

`ShopUI.OnDisable`에서도 `Close()`를 부르게 해뒀습니다.
UI 오브젝트가 어떤 이유로든 비활성화되면 모달 플래그가 켜진 채 남아
조작이 영영 안 먹는 상태가 되기 때문입니다.

### 2.19 상점: 담기와 확정을 나눈 이유

버튼을 누를 때마다 즉시 골드가 빠지는 방식이 제일 짧습니다.
하지만 잘못 누른 걸 되돌릴 방법이 없고,
"잔액이 부족한 순간"이 항목마다 흩어져서 안내 시점을 잡기 어렵습니다.

담기·빼기 단계에서는 `ShopUI`가 `Dictionary<ItemData, int>`에만 기록하고,
`Confirm()`에서 `Shop.TryBuy` / `TrySell`을 항목마다 불러 한 번에 정산합니다.
확정 전에는 아무것도 안 변하니 구매 금액과 구매 후 잔액을 미리 보여줄 수 있고,
잔액이 음수가 되면 확정 버튼을 잠글 수 있습니다.

거래 결과는 `bool` 대신 `TradeResult` 열거형으로 돌려받습니다.

```csharp
public enum TradeResult { Success, NotEnoughGold, NoItem, NotTradable, Invalid }
```

실패 사유가 하나가 아니어서, UI가 어떤 안내를 띄울지 정하려면 참·거짓만으로는 부족했습니다.
판단은 `Shop`이 하고 표현은 `ShopUI`가 하되, 판단 결과를 표현이 쓸 수 있을 만큼 구체적으로 넘긴 겁니다.

### 2.20 세이브: Dictionary를 그대로 저장할 수 없다는 것

저장할 상태가 일곱 군데에 흩어져 있었습니다.
인벤토리, 퀘스트 로그, 처치 집계, 지갑, 위치, 대화 플래그, 주운 아이템 목록.
한 클래스가 이걸 전부 아는 형태는 피하고 싶었습니다.

`SaveCoordinator`가 각 소유자에게서 값을 받아 `SaveData`로 옮기고,
불러올 때는 각 소유자의 `Restore()`를 부릅니다.
`SaveCoordinator`는 옮기기만 하고 해석하지 않습니다.

여기서 두 가지가 걸렸습니다.

**`JsonUtility`는 `Dictionary`를 직렬화하지 못합니다.**
그래서 저장 시점에 `List<CountEntry>`로 펴고, 불러올 때 다시 Dictionary로 접습니다.

**ScriptableObject 참조도 직렬화하지 못합니다.**
`ItemData` 참조를 그대로 넣으면 다음 실행에서 복원이 안 됩니다.
그래서 각 데이터 에셋에 `id` 문자열을 두고, 저장은 id로 하고,
불러올 때 `GameDatabase`에서 id로 되찾습니다.

```csharp
data.inventory.Add(new SaveData.CountEntry { id = pair.Key.id, count = pair.Value });
```

`GameDatabase`는 id → 에셋 매핑을 들고 있는 ScriptableObject입니다.
`OnValidate()`에서 id가 비었거나 중복된 걸 잡아냅니다.
id는 저장 파일의 키라서, 중복되면 조용히 잘못된 아이템이 복원됩니다.
런타임에 발견하면 늦으니 에디터에서 막았습니다.

주운 아이템은 개수만으로는 부족했습니다.
불러온 뒤 씬에 딸기가 그대로 남아 있으면 다시 주울 수 있으니까요.
`PickupTracker`가 주운 id를 `HashSet`으로 들고 있고,
복원할 때 씬의 `ItemPickup`을 훑어서 이미 주운 것만 비활성화합니다.

버전 필드도 넣었습니다. 저장 구조가 바뀌면 옛 파일을 그냥 읽어서 깨지는 대신
버전을 보고 거부합니다. 파일 IO는 전부 try/catch로 감쌌습니다.
저장 실패가 게임을 멈추게 할 이유는 없습니다.

### 2.21 구독은 이후의 변화만 전달한다

같은 원인의 버그를 세 번 만났습니다. 세 번째에야 패턴으로 정리됐습니다.

1. 체력 바가 `0 / 100`으로 시작함
2. 불러오기 후 퀘스트 트래커가 비어 있음
3. 첫 피격에 피격 모션이 안 나옴

전부 **이벤트를 구독하기 전에 이미 값이 바뀌어 있었던** 경우입니다.
구독은 그 이후의 변화만 전달합니다. 구독 시점의 현재 값은 알려주지 않습니다.

해결도 같습니다. 구독할 때 현재 상태를 한 번 읽습니다.

```csharp
private void OnEnable()
{
    lastHealth = health.Current;   // 구독 전에 일어난 변화를 놓치지 않도록
    health.OnHealthChanged += HandleHealthChanged;
}
```

체력 바는 초기 표시를 `Start()`로 옮겼습니다. `Start`는 모든 `Awake` 이후에 실행되니까요.
퀘스트 트래커는 이벤트 집계 대신 `QuestLog`의 상태를 직접 훑어서 표시할 퀘스트를 고르게 바꿨습니다.
2.10에서 얻은 결론이 UI에도 그대로 적용된 셈입니다.

### 2.22 클래스를 아직 나누지 않은 이유

`PlayerController`는 입력 읽기·이동·회전 셋을 담당합니다.
처음부터 `PlayerInputReader` / `PlayerMotor` / `PlayerController`로 나누는 안도 봤지만
지금은 안 나누기로 했습니다.

단일 책임 원칙은 "클래스당 기능 하나"가 아니라 **"바뀔 이유가 하나"**입니다.
지금 이 클래스는 이동 방식이 바뀔 때만 수정됩니다.
나누면 파일 수와 상호 참조만 늘고 얻는 게 없습니다.

대신 나눌 시점의 신호를 미리 적어뒀습니다.
`Update`가 30줄을 넘을 때, 상태 확인 분기가 두세 개 쌓일 때,
새 기능을 어디 넣을지 망설여질 때.

전투를 넣고 나서 실제로 `UIState` 확인과 넉백 처리가 들어왔습니다.
아직 30줄은 안 넘었지만 다음 기능이 하나 더 들어오면 나눌 자리입니다.

### 2.23 하드코딩을 데이터로 돌려보낸 정리

작업 후반에 저장소를 훑으면서 인스펙터와 코드에 흩어진 문자열을 정리했습니다.

| 정리 전 | 정리 후 |
|---|---|
| NPC마다 인스펙터에 이름을 직접 입력 | `NpcData.displayName`에서 가져옴 (`DisplayName` 오버라이드) |
| 아이템 픽업마다 표시 이름 입력 | `ItemData.displayName`에서 가져옴 |
| 적 이름표에 이름 직접 입력 | `EnemyData.displayName`에서 가져옴 |
| 애니메이터 파라미터 이름이 코드에 박힘 | `[SerializeField] string attackTrigger = "Attack"` 등으로 노출 |
| 대상 태그가 코드에 박힘 | `[SerializeField] string targetTag`로 노출 |

`Interactable.DisplayName`을 `virtual`로 바꾸고 각 파생 클래스에서 오버라이드하는 형태입니다.
이름 하나를 고치려고 씬의 오브젝트를 전부 찾아다니는 일이 없어졌습니다.

파일 인코딩도 이때 정리했습니다.
Visual Studio가 일부 파일을 CP949로 저장해서 GitHub에서 한글 주석이 깨져 있었습니다.
19개 파일을 PowerShell로 UTF-8(BOM 포함)로 일괄 변환했고, 지금은 66개 전부 UTF-8입니다.

## 3. 막혔던 문제와 해결

### 3.1 퀘스트가 완료로 넘어가지 않음

딸기를 다 모아도 NPC가 계속 "부족하다"고 했습니다. 상태는 `InProgress`에 고정.

완료 조건 분기에서 `questState = Completed`로 대입한 직후,
조건 밖에서 `questState = InProgress`를 무조건 다시 대입하고 있었습니다.
조건부 대입이 무조건 대입에 덮어써지는 구조였습니다.

재대입을 지우고 완료/미완료를 `if/else`로 갈라서 한쪽만 실행되게 했습니다.
이후 **"조건 안에서 바꾼 값을 조건 밖에서 다시 건드리지 않는다"**를 점검 항목으로 삼았습니다.

### 3.2 퀘스트를 받자마자 완료됨

수락 직후 다시 말을 걸면 딸기를 하나도 안 모았는데 완료 처리됐습니다.

비교 연산자를 `>=`가 아니라 `<=`로 썼습니다. `0 <= 3`이 참이라 첫 대화에서 조건이 성립했습니다.

부등호를 고치면서 `==` 대신 `>=`를 쓰도록 같이 바꿨습니다.
집계가 목표치를 넘는 경우에도 조건이 성립해야 합니다.
경계 조건은 정확한 일치보다 범위로 판정하는 편이 안전합니다.

### 3.3 수락 전에 주운 아이템이 진행도에 안 잡힘

3개를 먼저 주운 뒤 퀘스트를 받으면 진행도가 `0/3`으로 나왔습니다.

진행도를 수집 이벤트 집계로 만들고, 집계 조건을 `QuestState.InProgress`로 제한하고 있었습니다.
조건을 없애면 반대로 아이템을 쓴 뒤에도 집계가 남는 문제가 생겨서
조건 조정만으로는 해결이 안 됐습니다.

판정 근거를 사건 집계에서 인벤토리 상태 조회로 바꿨습니다(2.10).
획득 시점과 순서에 무관해졌습니다.
**"사건을 세지 말고 상태를 물어본다"**를 조건 판정의 기본 방침으로 삼았습니다.

### 3.4 동반자가 플레이어 주위를 계속 빙빙 돎

가장 오래 붙잡힌 문제였습니다. **원인이 두 겹이라** 증상만으로는 구분이 안 됐습니다.

따라오지 않거나, 따라오더라도 주위를 돌았습니다. 가까이 갈수록 심해졌습니다.

추측으로 파라미터를 만지는 대신 로그로 범위를 좁혔습니다.

1. 상태 전이 로그 → 전이는 정상
2. `isOnNavMesh` / `pathStatus` / `remainingDistance` → 경로는 유효한데 `remaining=0`
3. `position` / `target` / `destination` 비교 → **목적지가 자기 위치와 같음**
4. Idle에서 `position`과 `distance` 로그 → **플레이어가 다가오는데 거리가 증가**

**원인 1 — 계층 구조의 위치 오프셋.**
로직은 부모를 이동시키는데 실제로 보이는 모델은 자식이었고, 자식의 로컬 위치가 원점이 아니었습니다.
눈에 보이는 위치와 계산되는 위치가 서로 달랐습니다.
부모가 회전하면 오프셋된 자식이 부모를 중심으로 궤도를 그립니다. 이게 "선회"의 실체였습니다.

**원인 2 — 근거리에서 방향 벡터가 불안정.**
대상과 가까워질수록 방향 벡터의 크기가 작아져서, 미세한 위치 변화에도 정규화 결과가 크게 흔들립니다.
매 프레임 이 값으로 목표 회전을 갱신하면 회전이 진동합니다.

자식의 로컬 위치를 원점으로 맞추고, 자식은 크기·정면 축 보정만 맡게 역할을 나눴습니다.
회전 갱신은 실제로 이동할 때로 한정했습니다. 정지 상태에서는 방향을 계산하지 않으니 진동이 날 수 없습니다.

로그로 좁혀간 게 결정적이었습니다.
"보이는 것"이 아니라 **"계산되는 값"을 직접 확인**해야 원인이 나온다는 것,
그리고 증상 하나에 원인이 둘 이상일 수 있다는 걸 여기서 배웠습니다.

### 3.5 적이 붙으면 캐릭터가 떨리고 공격을 안 함

두 증상의 원인이 하나였습니다.

적은 `transform.position`을 직접 갱신해서 충돌을 무시하고 전진하는데,
플레이어의 `CharacterController`는 겹친 콜라이더에서 자신을 밀어냅니다.
매 프레임 서로 밀고 밀리면서 **거리가 진동**했습니다.

그 진동이 `attackRange`(진입)와 `attackExitRange`(이탈) 경계를 계속 넘나들어
Attack ↔ Chase 전이가 반복됐고, `AttackState.Enter()`에서 쿨다운 기준 시각이 매번 초기화돼
**쿨다운이 영원히 안 찼습니다.**

적 콜라이더를 트리거로 바꿔 물리적 밀어냄을 없앴습니다.
트리거는 이동을 막지 않지만 `Physics.OverlapSphere` 질의에는 여전히 잡히므로
양쪽 공격 판정은 그대로 동작합니다.

물리 상호작용이 상태 전이에 끼어들 수 있다는 것,
그리고 겉보기에 다른 두 증상이 하나의 원인에서 나올 수 있다는 걸 확인했습니다.

### 3.6 UI 초기 표시가 0으로 나옴

체력이 100인데 체력 바에 `0 / 100`. 피해를 입은 뒤엔 `90 / 100`으로 정상.

UI가 `OnEnable`에서 `Health.Current`를 읽는데,
그 시점에 `Health.Awake()`가 아직 안 돌아서 `Current`가 int 기본값 0이었습니다.
`Max`는 직렬화된 필드라 정상값이 읽혀서 "0 / 100"이라는 조합이 나왔습니다.
오브젝트 간 `Awake` 순서는 보장되지 않습니다.

구독은 `OnEnable`에 두고 초기 표시만 `Start()`로 옮겼습니다.

실행 순서를 강제(`DefaultExecutionOrder`)하기보다
**순서에 의존하지 않는 위치로 옮기는 편**이 견고합니다.
"이벤트가 안 온다"가 아니라 "구독은 됐는데 초기값을 잘못 읽었다"는 문제라서
원인 파악이 까다로웠습니다.

### 3.7 계층에 붙이면 로컬 좌표가 남는다 (재발)

캐릭터 머리 위 이름표가 화면에 안 보였습니다.

프리팹을 부모 밑으로 드래그할 때 유니티는 월드 위치를 유지합니다.
그래서 로컬 좌표가 `(2.67, -3.62, -8.18)`로 남았고,
이름표가 캐릭터 모델 안쪽에 들어가서 메시에 가려져 있었습니다.

**3.4와 같은 원인이 다른 형태로 재발한 것**이라
이후 계층에 오브젝트를 붙일 때 로컬 좌표 확인을 고정 점검 항목으로 넣었습니다.

### 3.8 NPC가 퀘스트를 두 개 가지면 대사가 비어서 나옴

마을 사람(딸기)과 사냥꾼(슬라임)을 배치하고 순서대로 진행하자
두 번째 NPC의 대사가 공백으로 나왔습니다.

`QuestGiver`가 **지금 말할 퀘스트를 고르는 단계 없이** 곧바로 대사를 선택하고 있었습니다.
NPC가 퀘스트를 하나만 가질 때는 안 드러나지만,
목록 앞쪽에 이미 완료된 퀘스트가 있으면 그 상태에 해당하는 대사(정의되지 않음)를 그대로 돌려줬습니다.
"상태가 하나뿐"이라는 전제 위에 코드가 서 있었던 겁니다.

`PickCurrentQuest()`를 만들어 **① 어떤 퀘스트를 말할지**와
**② 그 퀘스트가 어떤 상태인지**를 두 단계로 나눴습니다.

```csharp
foreach (QuestData quest in quests)
    if (log.GetState(quest) != QuestState.Completed)
        return quest;    // 목록 순서대로, 아직 끝나지 않은 첫 번째
```

선택 규칙은 일부러 단순하게 뒀습니다.
상태별 우선순위를 매기는 방식도 검토했지만, 지금 NPC가 갖는 퀘스트는 최대 두 개고
그 둘은 순서가 정해져 있습니다. 순서를 이미 아는 상황에서 우선순위 표를 만드는 것은
읽는 사람만 늘어나는 규칙이라고 봤습니다.
**퀘스트 배열의 순서 자체가 곧 진행 순서**라는 약속으로 충분했습니다.

한 NPC가 서로 무관한 퀘스트를 여러 개 갖게 되면 그때 우선순위가 필요해집니다.
그 시점이 규칙을 넣을 시점이지, 지금은 아니라고 판단했습니다.

NPC가 퀘스트를 몇 개 갖든 같은 코드로 처리됩니다.
나중에 넣은 "선행 퀘스트를 끝내야 열리는 잠금 대사"도 분기 하나 추가로 끝났습니다.
분기를 늘리는 대신 **선택과 표현을 나눈 것**이 확장을 흡수했습니다.

### 3.9 적 이름표와 체력 바가 갱신 안 됨

이름이 안 나오고 체력 바는 늘 가득 찬 상태였습니다. 피해 로그는 `70/100`처럼 정상으로 찍혔습니다.

**원인 하나.** 이름표 프리팹에 UI 오브젝트(Canvas·Image·Text)만 들어 있고
이걸 구동하는 `Nameplate` 컴포넌트가 빠져 있었습니다.
`Health`는 이벤트를 정상적으로 쏘고 있었지만 **구독자가 없었습니다.**
로그로 데이터 경로를 먼저 확인해 둔 덕분에 코드가 아니라 씬 구성 쪽을 볼 수 있었습니다.

**원인 둘.** 컴포넌트를 붙인 뒤에도 채움 이미지가 배경을 꽉 못 채웠습니다.
화면 픽셀을 재보니 상하좌우로 균일하게 8%씩 작았습니다.
값이 모자란 거라면 한쪽만 어긋나야 하는데 대칭이었습니다.
이 대칭성이 "수치 문제가 아니라 그리는 방식의 문제"를 가리켰습니다.

`Image Type = Filled`는 9-슬라이스를 무시하고 스프라이트를 통째로 늘립니다.
그래서 내장 스프라이트의 투명 여백까지 같이 확대됐습니다.
`Sliced`는 테두리를 원본 크기로 유지하니까 이 문제가 안 보였던 겁니다.

프리팹에 컴포넌트를 넣고, 같은 실수가 반복되지 않게
`Nameplate`가 `GetComponentInParent<Health>()`로 대상을 스스로 찾도록 바꿨습니다
(2.6의 기준 — 계층이 보장되는 관계는 탐색, 아니면 주입).
이름도 `EnemyData.displayName`에서 가져오게 해서 개체마다 손으로 안 넣게 했습니다.
채움 이미지는 스프라이트 여백에 의존하지 않는 방식으로 폭을 조절하게 고쳤습니다.

적을 복제해도 인스펙터 연결 없이 이름과 체력이 나옵니다.
증상이 하나여도 원인이 둘일 수 있다는 것,
그리고 **어긋남이 대칭인지 비대칭인지**가 원인을 가르는 단서가 된다는 걸 확인했습니다.

### 3.10 공격할 때만 T포즈가 됨

무기를 든 이동 모션이 필요해서 다른 애니메이션 팩을 붙였더니
이동은 되는데 공격 순간에만 T포즈가 나왔습니다.

리그가 달라서였습니다.
**Generic 리그의 애니메이션은 본 경로(bone path)를 기준으로 재생됩니다.**
스켈레톤 구조가 다른 캐릭터에 붙이면 대응되는 본을 못 찾아 기본 자세로 떨어집니다.
Humanoid 리그였다면 아바타를 통해 매핑되니 공유가 됐을 겁니다.

애니메이션을 캐릭터에 맞추는 대신 **캐릭터를 애니메이션에 맞췄습니다.**
검·방패 모션이 처음부터 들어 있는 모델(RPG Tiny Hero Duo)로 교체하고,
애니메이터 컨트롤러를 새로 짰습니다.
손 슬롯 두 개를 만들어 무기와 방패를 붙였고, 직업별 장비 교체(2.12)도 여기 얹혔습니다.

교체하면서 애니메이터 전이 설정도 같이 손봤습니다(부록 참조).

### 3.11 빌드에서만 저장이 동작하지 않음

가장 늦게 발견했고, 원인을 알고 나니 가장 부끄러웠던 문제입니다.

에디터에서는 `F5`·`F9`가 정상 동작했는데 빌드한 실행 파일에서만 아무 반응이 없었습니다.
저장 파일도 생기지 않고, 에러도 뜨지 않았습니다.

에디터에서는 게임 씬을 직접 열어 실행했고, 빌드는 직업 선택 씬부터 시작한다는 차이가 있었습니다.
씬을 두 개 거칠 때만 재현된다는 것을 확인하고 나서 원인이 좁혀졌습니다.

`SaveCoordinator`가 `GameManager` 오브젝트에 붙어 있었습니다.
`GameManager`는 `DontDestroyOnLoad` 대상이고, 싱글톤 중복 가드가 이렇게 되어 있습니다.

```csharp
if (Instance != null && Instance != this)
{
    Destroy(gameObject);   // 컴포넌트가 아니라 오브젝트를 통째로
    return;
}
```

직업 선택 씬의 `GameManager`가 먼저 `Instance`를 차지하고 살아남습니다.
게임 씬이 로드되면 그 씬의 `GameManager`는 중복이므로 파괴되는데,
같은 오브젝트에 얹혀 있던 `SaveCoordinator`도 함께 사라집니다.
입력을 받을 스크립트가 아예 없으니 아무 일도 일어나지 않았던 것입니다.

`SaveCoordinator`를 독립된 오브젝트로 분리해 해결했습니다.

이 문제가 뼈아팠던 이유는, **2.3에서 제가 직접 세운 규칙을 제가 어겼기 때문**입니다.

> 살아남는 객체는 상태와 이벤트만 보유하고, 씬 오브젝트 참조를 캐싱하지 않음

`GameManager` 자체는 이 규칙을 지키고 있었습니다. 갖고 있는 건 에셋 참조뿐입니다.
그런데 `SaveCoordinator`는 플레이어의 `Transform`과 `PlayerProgress`를 참조합니다.
씬과 함께 죽고 태어나야 하는 컴포넌트를 **씬을 넘어 살아남는 오브젝트에 얹으면서** 규칙이 깨졌습니다.

두 가지를 얻었습니다.
씬 안의 것을 참조하는 컴포넌트는 씬과 수명이 같아야 한다는 것,
그리고 **에디터에서 씬을 직접 열어 실행하는 습관이 씬 전환 관련 결함을 가려준다**는 것입니다.
이후로는 기능을 마무리할 때 빌드로 한 번 확인하는 것을 절차에 넣었습니다.

## 4. AI 활용 기록

이 프로젝트는 생성형 AI를 개발 보조로 사용했습니다.
어디까지 맡기고 어디부터 직접 판단했는지 적어둡니다.

### 작업 방식

코드를 먼저 받아 쓰는 대신, **직접 설계·작성한 뒤 리뷰를 받는** 순서로 진행했습니다.
문제를 만나면 먼저 스스로 접근 방식을 정리하고, 그 판단을 검증하는 데 AI를 썼습니다.
막힌 지점은 완성된 코드를 통째로 받기보다 구조와 힌트를 받아 직접 작성했습니다.

### 직접 판단한 것

- 전체 아키텍처와 시스템 간 통신 방식 (싱글톤 최소화 + 이벤트)
- 상호작용 판정 방식과 그 근거
- 이동 컴포넌트 선택, 넉백 처리 방침
- 게임 상태 정의와 `SetState` 로직
- 참조 주입 기준 (인스펙터 주입 vs 런타임 캐싱)
- 클래스 분리 시점과 분리 신호
- 스코프 결정 (전투·상점 추가, 작물 재배·풀링 제외)
- 캐릭터 교체 판단 — 애니메이션을 리그에 맞추는 대신 모델을 바꾸는 쪽

### AI로 가속한 것

- 작성한 코드 리뷰와 개선점 확인
- 익숙하지 않은 API·에디터 동작 확인 (`JsonUtility` 제약, `Image` 렌더링 규칙 등)
- 인코딩 일괄 변환 스크립트 같은 반복 작업
- 버그 원인 후보를 좁힐 때의 가설 정리

### 제안을 받아들이지 않은 것

| 제안 | 안 쓴 이유 | 실제로 택한 것 |
|---|---|---|
| 제네릭 싱글톤 베이스 `Singleton<T>` | 매니저가 GameManager 하나뿐. 하나 있는 상태에서 추상 클래스부터 만드는 건 과설계 | 단일 클래스에 직접 구현 |
| ScriptableObject 기반 이벤트 시스템 | 유니티에서 흔한 패턴이지만 이 규모에선 에셋 파일만 늘고 얻는 게 적음 | C# `event Action` |
| 게임 전역 상태를 정식 상태머신으로 | 상태머신은 "여기서 저기로만 갈 수 있다"는 제약이 있을 때 값어치가 있음. 전역 상태는 어디서든 Paused로 갈 수 있어 제약이 거의 없음 | enum + `SetState`. 상태머신은 AI에만 적용 |
| 카메라 참조를 인스펙터 주입 | 프리팹이 씬 오브젝트 참조를 직렬화 못 해서, Player를 프리팹화하면 null | `Awake` 탐색 + 실패 시 `LogError` |
| 처음부터 `PlayerInputReader`/`PlayerMotor`로 분리 | 지금 책임이 "이동" 하나로 응집됨. 파일 수와 상호 참조만 증가 | 단일 클래스 유지, 분리 신호를 미리 정의 |
| 확장 가능한 스탯 시스템 (레벨·능력치 계수) | 실제로 쓰이는 수치는 체력·공격력·이동속도·방어력 넷. 안 쓰는 구조를 남기는 건 확장성이 아니라 스코프 판단 실패 | `ClassData`에 필요한 넷만 |
| 체력 바를 스프라이트 없이 rect 크기로 직접 제어 | 문제 원인은 `Image Type` 설정이었지 코드가 아니었음. 에디터 설정으로 되는 걸 코드로 우회하면 다음 사람이 이유를 모름 | 설정을 고치고 코드는 원래대로 |

마지막 항목은 작업 중에 실제로 되돌린 사례입니다.
코드로 우회하는 방향으로 한참 갔다가, 인스펙터 설정 하나면 되는 일이라는 걸 확인하고 되돌렸습니다.

### 추상화 시점 기준

작업 중 "미리 일반화해둘까"를 반복해서 마주쳐서, 기준을 하나 정하고 일관되게 적용했습니다.

> **두 번째 사례가 실제로 나타났을 때 추상화한다.**

- 매니저가 둘이 되면 → 싱글톤 베이스 추출 (해당 없음)
- 플레이어와 적이 모두 체력을 쓰면 → `Health` 공유 (해당됨)
- 플레이어와 적이 모두 피격 반응이 필요하면 → `HitReaction` 공유 (해당됨)
- 캐릭터가 둘 이상이 되면 → 스탯 시스템 (직업이 셋이 되면서 해당됨 → `ClassData`)

하나뿐인 상태에서 만드는 건 추측이고, 둘이 된 뒤 만드는 건 설계라고 봤습니다.
`HitReaction`은 원래 `EnemyHitReaction`이라는 이름으로 적 전용이었는데,
플레이어에게도 같은 게 필요해진 시점에 이름을 바꾸고 공유했습니다.

## 6. 실행 방법

```
1. Unity 6 (6000.5.9f1) 이상 · URP 로 프로젝트 열기
2. Assets/_Project/Scenes/ClassSelect.unity 를 열고 재생
   (직업 선택을 건너뛰려면 SampleScene 을 직접 열어도 됩니다.
    이 경우 PlayerClassApplier 의 Fallback Class 값이 적용됩니다)
```

| 조작 | 키 |
|---|---|
| 이동 | `W` `A` `S` `D` |
| 상호작용 (대화 · 획득 · 상점 열기) | `E` |
| 공격 | 마우스 좌클릭 |
| 인벤토리 열기 / 닫기 | `I` |
| 아이템 사용 | 인벤토리에서 아이템 클릭 |
| 상점 닫기 | `Esc` |
| 저장 / 불러오기 | `F5` / `F9` |

저장 파일은 `Application.persistentDataPath/save.json`에 생깁니다.
윈도우 기준 `%USERPROFILE%\AppData\LocalLow\<회사명>\<프로젝트명>\save.json`입니다.

## 7. 남은 과제

프로토타입 범위에서 알고 남겨둔 것들입니다.
모르고 지나간 것과 알고 남긴 것은 다르다고 생각해서 적어둡니다.

| 항목 | 현재 상태 | 해결 방향 |
|---|---|---|
| 동반자의 장애물 회피 | 플레이어 위치만 보고 직진해서 적이나 오브젝트를 통과합니다. NavMesh를 걷어내면서(2.16) 회피도 같이 빠졌습니다 | 전투 중 유지 거리를 늘리거나 `FleeState`를 추가해 적 근처를 피하도록 상태 확장 |
| 적 종류 | 슬라임 한 종만 있습니다 | 수치가 이미 `EnemyData`로 분리돼 있어(2.11) 모델과 에셋만 추가하면 코드 변경 없이 확장됩니다 |
| NPC 연출 | 모델은 배치했지만 대기 애니메이션이 없어 서 있기만 합니다 | `NpcData`에 애니메이터 컨트롤러 필드를 추가하면 아이템·적과 같은 구조로 처리됩니다 |
| `ClassData.modelPrefab` | 필드는 있는데 비어 있습니다. 세 직업이 같은 몸체를 쓰고 장비만 다릅니다 | 직업별 모델이 생기면 `PlayerClassApplier.Apply`에서 몸체 교체를 추가 |
| 저장 슬롯 | 슬롯이 하나입니다 | 파일명에 인덱스를 붙이고 `SaveSystem`에 슬롯 인자를 추가 |

## 부록. 에디터 설정 메모

코드가 아니라 **에디터 설정 때문에 원인을 못 찾고 시간을 쓴 것들**을 정리해 뒀습니다.
같은 걸 다시 만났을 때 찾아보려고 남깁니다.

### 머티리얼이 분홍색으로 보일 때

셰이더를 못 찾았다는 뜻입니다.
Built-in 파이프라인용 에셋(`Standard` 셰이더)을 URP 프로젝트에 임포트하면 이렇게 됩니다.

**한 번에 고치기**
`Window > Rendering > Render Pipeline Converter`
→ `Built-in to URP` 선택 → `Material Upgrade` 체크 → `Initialize And Convert`

**하나만 고치기**
머티리얼 선택 → Inspector 맨 위 `Shader` 드롭다운 → `Universal Render Pipeline > Lit`
(투명한 것은 `Surface Type`을 `Transparent`로 같이 바꿔야 합니다)

셰이더를 바꾸면 텍스처 슬롯이 초기화되는 경우가 있으니
`Base Map`에 원래 텍스처가 그대로 붙어 있는지 확인해야 합니다.

### 애니메이션 Loop Time이 회색이라 못 끌 때

FBX 안에 들어 있는 클립은 **읽기 전용**입니다. 그래서 체크박스가 비활성입니다.

두 가지 방법이 있습니다.

**FBX 임포트 설정에서 바꾸기**
Project 창에서 FBX 파일 선택 → Inspector → `Animation` 탭
→ Clips 목록에서 해당 클립 선택 → 아래 `Loop Time` 체크 → **`Apply`**
(Apply를 안 누르면 반영이 안 됩니다. 여기서 제일 많이 놓칩니다)

**클립을 복제해서 바꾸기**
Project 창에서 FBX를 펼치면 안에 클립이 보입니다.
클립 선택 → `Ctrl + D` → 프로젝트 폴더에 편집 가능한 `.anim`이 생깁니다.
이걸 Animator 상태에 넣으면 Loop Time을 자유롭게 켜고 끌 수 있습니다.
FBX를 다시 임포트해도 설정이 안 날아간다는 게 장점입니다.

Idle·Walk·Run은 Loop Time 켜고, Attack·GetHit·Die는 꺼야 합니다.
공격 모션을 루프로 두면 무한히 휘두릅니다.

### Animator 전이가 한 박자 늦을 때

`Has Exit Time` 때문입니다. 이건 "현재 모션을 몇 % 재생한 뒤에 넘어갈지"를 정하는 값이라,
켜져 있으면 조건이 만족돼도 그 시점까지 기다립니다.

| 전이 | Has Exit Time | 이유 |
|---|---|---|
| Idle → Move | **끔** | 키를 누른 즉시 움직여야 함 |
| Move → Idle | **끔** | 키를 뗀 즉시 멈춰야 함 |
| Any State → Attack | **끔** | 클릭 즉시 나가야 함 |
| Attack → Idle | **켬** | 모션이 끝나고 돌아와야 함 |
| GetHit → Idle | **켬** (Exit Time 0.7 정도) | 1.0으로 두면 경직이 너무 길게 느껴짐 |

`Transition Duration`도 같이 봐야 합니다. 기본값 0.25초는 반응이 느리게 느껴집니다.
이동 전이는 0.05~0.1이 낫습니다.
`Settings`를 펼쳐야 이 값들이 보이고, 아래 타임라인 그래프에서 드래그로도 조절됩니다.

### Animator 컴포넌트는 어디에 붙나

**스킨드 메시가 들어 있는 오브젝트**, 보통 모델 프리팹의 루트에 붙습니다.
빈 부모 오브젝트에 붙이면 본을 못 찾아서 아무 일도 안 일어납니다.

스크립트는 부모에 있어도 됩니다.
다만 참조를 인스펙터로 직접 연결하거나 `GetComponentInChildren<Animator>()`로 찾아야 합니다.
이 프로젝트는 인스펙터 연결 방식이고, 비어 있으면 자식에서 찾도록 폴백을 뒀습니다.

### 리그(Rig) 종류

FBX 선택 → Inspector → `Rig` 탭 → `Animation Type`.

- **Generic** — 본 이름과 경로를 기준으로 재생합니다. 스켈레톤 구조가 같아야만 애니메이션 공유가 됩니다.
- **Humanoid** — 아바타를 통해 표준 본에 매핑합니다. 사람형이면 구조가 달라도 공유됩니다.

**다른 캐릭터의 애니메이션을 붙였는데 T포즈가 나온다면 대부분 이것 때문입니다.**
Generic끼리 스켈레톤이 안 맞아 대응 본을 못 찾은 겁니다.
사람형 캐릭터를 여러 개 쓸 계획이면 처음부터 Humanoid로 임포트해두는 게 낫습니다.

### Image의 Fill Amount가 안 먹을 때

**`Source Image`가 `None`이면 `fillAmount`는 아무 효과가 없습니다.**
그릴 스프라이트가 없으면 유니티가 메시 생성을 건너뛰기 때문입니다.
체력 바가 안 줄어드는데 로그는 정상이라면 여기부터 봐야 합니다.

그리고 `Image Type`에 따라 스프라이트를 늘리는 방식이 다릅니다.

| Image Type | 9-슬라이스 테두리 | 결과 |
|---|---|---|
| `Sliced` | 원본 크기 유지 | 모서리가 안 늘어남. 대신 `fillAmount` 못 씀 |
| `Filled` | **무시하고 통째로 늘림** | 스프라이트의 투명 여백까지 같이 커짐 |

`Preserve Aspect`는 `Simple`과 `Filled`에만 있고 `Sliced`에는 없습니다.

### 자식으로 붙일 때 로컬 좌표

프리팹을 Hierarchy에서 다른 오브젝트 밑으로 드래그하면
**유니티는 월드 위치를 유지하려고 로컬 좌표에 보정값을 넣습니다.**
그래서 붙이자마자 Position이 `(2.67, -3.62, -8.18)` 같은 값이 됩니다.

붙인 다음 Transform 컴포넌트 우클릭 → `Reset`,
또는 Position을 직접 `0, 0, 0`으로 넣으세요.
이 프로젝트에서 이 문제로 두 번 시간을 썼습니다(3.4, 3.7).

### 콜라이더를 Is Trigger로 두면

물리적으로 밀지 않게 되지만 `Physics.OverlapSphere` 질의에는 **여전히 잡힙니다.**
공격 판정은 살리면서 밀림만 없애고 싶을 때 쓸 수 있습니다(3.5).

`Physics.OverlapSphere`가 트리거를 무시하게 하려면
`Physics.queriesHitTriggers`를 끄거나 오버로드의 `QueryTriggerInteraction`을 넘겨야 합니다.

### 한글 주석이 GitHub에서 깨질 때

스크립트 파일 인코딩 문제입니다.
Visual Studio가 CP949(949)로 저장한 파일을 유니티와 GitHub은 UTF-8로 읽습니다.

VS에서 한 파일씩 고치려면
`파일 > 다른 이름으로 저장` → 저장 버튼 옆 화살표 → `인코딩하여 저장`
→ `유니코드(서명 있는 UTF-8) - 코드 페이지 65001`

파일이 많으면 PowerShell로 한 번에 처리하는 게 빠릅니다.
`Get-Content -Encoding Default`로 읽어서 `Set-Content -Encoding UTF8`로 다시 쓰면 됩니다.

### 프리팹은 씬 오브젝트를 참조할 수 없다

프리팹의 `[SerializeField]`에 씬에 있는 오브젝트(메인 카메라, 매니저 등)를 넣으면
저장은 되는 것처럼 보여도 인스턴스화 시점에 `None`이 됩니다.
프리팹은 씬 바깥의 에셋이라 씬 안의 것을 가리킬 수 없습니다.

같은 프리팹 안의 자식은 참조할 수 있습니다.
씬에 하나뿐인 전역 오브젝트는 런타임에 찾아야 합니다(2.6).
